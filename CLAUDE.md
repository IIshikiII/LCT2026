# LCT2026 — сервис прогнозирования аварий инженерных коллекторов Москвы

Хакатон «Международный хакатон 2026», задача 8 (ЖКХ). Итоговый продукт по ТЗ:
предиктивная ML-модель + веб-интерфейс диспетчера ОДС (дашборд рисков, карта
объектов, журнал прогнозов) + модуль автоматического формирования заявок на
превентивное обслуживание + REST API.

Требования ТЗ, проверяемые числами: горизонт прогноза ≥ 24 ч, время
формирования прогноза < 5 мин, задержка обработки потока < 5 мин.

Precision 0,7 и Recall 0,5 порогом приёмки не являются. ТЗ §9 требует вывести их
из качества данных, и заказчик подтвердил это на QA-сессии: это значения по
умолчанию, администратор их правит, команда ставит свои с обоснованием. Цель
хранится на направление. Горизонт в 24 часа тоже является умолчанием.

## Работа с git

## Три операционные системы

Разработка идёт на Windows и на macOS, прод на Ubuntu 22.04. Код обязан
работать везде. Четыре правила закрывают всё, на чём мы уже обожглись.

1. **В строках соединения писать `127.0.0.1`, а не `localhost`.** На Windows
   имя разрешается сначала в IPv6, Docker публикует порт и на `::`, но
   соединение туда не устанавливается. Клиент ждёт таймаута системы. Замер: 130
   секунд на каждый запуск pytest. Для адресов в браузере `localhost` годится.
2. **Порты публиковать только на петле.** В `docker-compose.yml` это
   `"${BIND_HOST:-127.0.0.1}:порт:порт"`. На Ubuntu опубликованный Docker порт
   обходит `ufw`, потому что правила DNAT попадают в таблицу `nat` раньше
   правил `ufw` в `filter`.
3. **Путь к интерпретатору различается.** Ubuntu и macOS дают
   `.venv/bin/python`, Windows даёт `.venv\Scripts\python.exe`. В документах
   называть обе формы, в скриптах определять систему.
4. **Переносы строк в репозитории LF.** Это задаёт `.gitattributes`. Скрипт с
   CRLF не запускается на Linux.

Обвязка автономного цикла в `loop/` работает только на Windows: она написана на
PowerShell и зовёт `taskkill`, `npm.cmd` и Windows API. Это инструмент
разработчика, в прод он не едет и в сборку не входит.

## Документация и любой текст

Правила письма лежат в `STE.md` (ASD-STE100 Simplified Technical English).
Читать их перед тем, как писать спецификацию, README, документ в `docs/`, ADR,
сообщение об ошибке, описание pull request или комментарий в коде.

Что это значит на практике: активный залог, один термин на одно понятие, простое
слово вместо канцелярского, одна мысль в предложении, предложение до 20–25 слов,
абзац до шести предложений, условие перед командой, шаги — нумерованным списком.
Не писать «осуществляется формирование» там, где годится «формирует». Не писать
преамбул и итоговых абзацев: только запрошенный текст.

Режимы из `STE.md`: strict — для процедур, ранбуков и текстов ошибок;
STE-flavoured — для остальной прозы. Словарные ограничения относятся к
английскому тексту; структурные правила (залог, длина, один термин, отсутствие
точки с запятой и тире-пунктуации) действуют и в русских документах.

Направления прогнозирования: пожар, несанкционированный доступ, отказ датчика,
подтопление. Модели есть у доступа и подтопления. Пятое, переохлаждение участка,
лежит в реестре выключенным и держит тест на гибкость: ТЗ его не называет, но
данные его держат, а заказчик разрешил свои сценарии прямо. Все направления
приводятся к одному формату: вероятность события на объекте в окне N часов,
N ≥ 24.

Требование «горизонт не менее 24 часов» имеет второе прочтение, и его тоже
учитывать при создании модели: прогноз даётся заранее, минимум за 24 часа до
начала окна. Смысл этого прочтения в плановом наряде, а не в вызове «здесь и
сейчас». Модель доступа замерила оба прочтения и выбрала первое: прогноз на ближайшие
сутки, потому что сейчас вызовы реактивны и постоянной охранной бригады нет
(`backend/docs/adr/0001-access-target.md`, правки от 25 и 26 сентября).

Единица прогноза это тройка «объект, галерея, пикет», 3 947 штук. Пикет равен
10 метрам и является контейнером оборудования. Разбор в `INSIGHTS.md` §1.4 и §4.

## frontend/

Стек: Vite 8 · React 19 · TypeScript 6 strict · React Router 7 (всё состояние UI
в URL, глобального стора нет) · TanStack Query 5 (опрос `refetchInterval: 60_000`)
· Tailwind v4 (токены в `src/styles/tokens.css`, через `@theme` в `src/index.css`)
· MapLibre GL · Recharts · zod + react-hook-form · MSW + faker (моки) · Vitest +
Testing Library · oxlint.

Скрипты: `npm run dev` · `build` · `typecheck` · `lint` · `test`.
Перед коммитом все четыре должны быть зелёными.

Приложение обязано полностью работать на моках: `VITE_USE_MOCKS=true` в `.env`.

Заглушки целиком лежат в `frontend/src/mocks/` и представляют собой стенд-ин
бэкенда, а не тестовые фикстуры. Направления прогнозирования реализованы там
плагинами — по файлу на каждое из четырёх. Ничто вне этой папки из неё не
импортирует, кроме `src/main.tsx` и двух файлов в `src/test/`.

Порядок работы принят такой: сначала документация, потом тест, потом код.
Правка контракта API без правки `docs/02-api-contract.md` и мок-хендлера в том
же коммите считается незавершённой.

### Архитектурные правила (см. spec §2, §8, §13) — не нарушать

1. **`Direction`, `level`, `status` — это `string`, а не union.** Никаких
   `type Direction = 'FIRE_RISK' | ...`. Ни одного `switch` по коду направления.
2. **Тело карточки прогноза — массив блоков `{ type, title, data }`** из API,
   рендерится через реестр `type → компонент` + запасной `GenericBlock`.
3. **Действия приходят из API** и уходят в один эндпоинт
   `POST /predictions/{id}/actions/{code}`. Не заводить ручку под каждую кнопку.
4. **Неизвестное не роняет экран.** Разбор ответов через `zod` с `.passthrough()`
   и `safeParse`; лишнее поле — не ошибка.
5. Состав экранов, колонок журнала, виджетов дашборда, справочников причин —
   из `GET /meta`, с запасными конфигами в `src/shared/config/`.
6. Периметр — ровно 4 экрана (`/`, `/map`, `/journal`, `/orders`) + правая
   панель карточки. Не расширять, пока эти четыре не закончены.

Тест на гибкость: добавить в мок `/meta` новое направление — оно должно само
появиться в фильтрах, на карте и на дашборде без правок кода. Проверяется
тестом `frontend/src/mocks/flexibility.test.tsx`, тумблер — в дев-панели
(правый нижний угол при `VITE_USE_MOCKS=true`).

Правила 1 и 6, а также изоляция заглушек, проверяются тестом
`frontend/src/architecture.test.ts`: он читает исходники и падает на union-типе
по коду направления, на `switch` по нему, на доменных словах вне `src/mocks/` и
на постороннем импорте из заглушек.
