# База данных и миграции

Схему создаёт нумерованный SQL. Alembic не используется: спецификация §2
объясняет причину.

## Как применить миграции

```
docker compose run --rm pipeline uv run --no-sync python -m app.cli migrate
```

Команда применяет неприменённые файлы по возрастанию номера. Каждый файл идёт
в своей транзакции. Применённые версии лежат в таблице `schema_migration`.
Повторный запуск не делает ничего.

## Как добавить миграцию

1. Создайте файл `migrations/NNN_имя.sql` со следующим свободным номером.
2. Пишите только прямое изменение. Откат — отдельный файл.
3. Проверьте имя: запускалка падает на файле не по образцу `NNN_имя.sql`.
4. Примените миграцию командой выше.
5. Опишите новые таблицы в этом документе.

## Правила схемы

Направление, уровень и статус лежат как `text`. Ни `ENUM`, ни `CHECK` со
списком значений. Причина — правило спецификации §5: новое направление
обязано появиться без миграции.

Таблица `alarm_event` партиционирована по месяцу штатными средствами
PostgreSQL. Расширения СУБД не нужны. Сейчас есть одна запасная партиция
`alarm_event_default`. Помесячные партиции создаст загрузка данных.

Уникальный индекс `prediction_unique_idx` по паре объекта, направления и окна
времени закрывает требование идемпотентности прогона из §7.

Колонка `work_order.prediction_id` обязательна. Заявка всегда рождается из
прогноза, а форма закрытия берёт список причин по направлению прогноза.
Хранить `direction` копией на заявке не стали: это второй источник истины,
который может разойтись с первым.

Таблица `sensor_reading` хранит показания датчиков и питает
`GET /predictions/{id}/timeseries`. Таблица `alarm_event` хранит дискретные
события, а `weather_hourly` — данные по району, поэтому графики карточки они не
закрывают.

## Две колонки прогноза, которые легко перепутать

Колонка `blocks` — витрина для диспетчера. Блок `factors` несёт подпись фразой,
вес и отформатированное значение вроде `37 %`. Пунктов там несколько, а не все.
Блокам разрешено быть неполными и битыми: неизвестный тип фронт рисует запасным
компонентом.

Колонка `features` — вход модели: имя признака к числу. Наружу она не отдаётся.
По ней через полгода можно воспроизвести решение модели, когда сырьё уже
изменилось.

Витрина источником данных не является. Разбор — в
[06-labels-and-metrics.md](06-labels-and-metrics.md).

## Определения таблиц в коде

Каталог `app/tables/` держит те же таблицы объектами `sqlalchemy.Table`. ORM
нет по спецификации §2. Схему создаёт SQL, а эти объекты строят запросы с
параметризацией.

Правка миграции без правки `app/tables/` в том же коммите считается
незавершённой. Расхождение ловит тест `tests/test_tables.py`: он сравнивает
описанные колонки с `information_schema` после применения миграций.

## Две группы таблиц

Таблицы делятся по тому, кто автор данных. Группы живут по разным правилам.

**Наш выход.** `facility`, `prediction`, `work_order`, `action_log`,
`pipeline_run`, `model_metric`, `collector`, `schema_migration`. Форму диктует
контракт фронта, поэтому она устойчива. Эндпоинты чтения работают почти целиком
с этой группой.

**Данные СМВУ.** `alarm_event`, `sensor_reading`, `sensor`, `weather_hourly`,
`ingest_state`. Их наполняет загрузчик выгрузки и поток СМВУ (ADR 0017) или
синтетика. `fault_log`, `repair`, `permit`, `inspection` источника не получат
никогда: так заказчик ответил во время QA-сессии. Они ждут удаления.

## Таблицы

| Таблица | Что хранит |
|---|---|
| `facility` | Единица прогноза. `kind`: пикет, участок или объект без пикета. Объект выгрузки, галерея, пикет, координата вдоль линии (ADR 0017). Пикет ссылается на свой участок полем `parent_id` (ADR 0018) |
| `sensor` | Датчик, его единица и канал выгрузки: номер, тип, название |
| `alarm_event` | События СМВУ. У события потока есть номер источника и момент приёма |
| `sensor_reading` | Температура и метан: наибольшее значение канала за час |
| `ingest_state` | Состояние загрузки: неделя потока, сдвиг времени, итог (ADR 0017) |
| `fault_log` | Журнал неисправностей датчиков ОДС |
| `repair` | История ремонтов и ТО |
| `permit` | Допуски и заявки на работы АРМ-Контроль |
| `inspection` | Визуальные обследования ОЭ |
| `weather_hourly` | Погода по районам. Ряд Москвы под районом `MOSCOW` читает подтопление |
| `flood_water_day` | Сутки пикета с сигналом затопления: вода или плановая проверка (ADR 0013) |
| `maintenance_window` | Окна плановых работ объекта: ППР датчиков метана и ТО (ADR 0016) |
| `prediction` | Прогноз: вероятность, уровень, горизонт, блоки объяснения, снимок признаков |
| `work_order` | Заявка на превентивное обслуживание. Открытая заявка на объект и направление одна (миграция 016) |
| `app_user` | Учётная запись: роль, область видимости, пароль, ключ второго фактора |
| `action_log` | Аудит: вход, выход и каждое действие над прогнозом и заявкой |
| `pipeline_run` | Прогон конвейера: длительность, число новых карточек, задержка потока |
| `model_metric` | Precision и Recall по направлению и наивного правила на той же выборке |
| `collector` | Трассы коллекторов для подложки карты |
| `schema_migration` | Применённые миграции |

## Статусы прогона конвейера

Колонка `pipeline_run.status` принимает три значения.

| Значение | Что означает |
|---|---|
| `RUNNING` | прогон идёт, значение по умолчанию |
| `DONE` | прогон закончился успешно |
| `FAILED` | прогон упал, причина лежит в `error` |

Здоровье конвейера считается только по последнему прогону в статусе `DONE`.
Прогон в работе за последний не считается: иначе свежесть данных показывала бы
успех, которого ещё не было. Конвейер задачи 10 обязан писать эти же значения,
константа лежит в `app/api/metrics.py`.

## DTO ответов

Каталог `app/schemas/` держит pydantic-модели ответов. Они зеркалят
`frontend/src/shared/api/schemas.ts` поле в поле.

Поля пишутся в snake_case и уходят наружу в camelCase: база `Dto` ставит
`alias_generator=to_camel` и `populate_by_name=True`. Отдавать ответ только
через `model_dump(by_alias=True)`.

Поля `direction`, `level` и `status` объявлены как `str`. Enum здесь означал бы
миграцию и правку схем на каждое новое направление.

Тест `tests/test_schemas.py` падает, когда ключ ответа перестал быть camelCase
или когда одно из трёх полей выше стало перечислением.

## Реестры интерфейса

Справочники `/meta` живут в коде, а не в базе. Каталог `app/meta/` держит:

| Файл | Что |
|---|---|
| `directions.py` | Пять направлений: подпись, цвет, горизонт, причины, типы работ |
| `catalog.py` | Уровни риска с порогами, статусы с цветом, районы, колонки, виджеты |
| `build.py` | Сборка ответа `GET /meta` из двух файлов выше |

Добавить направление — значит добавить одну запись в `directions.py`. Роутеры,
схемы и миграции при этом не меняются. Это проверяет
`tests/test_meta_flexibility.py`.

Направление `FLOOD_RISK` выключено по умолчанию. Включает его переменная
`ENABLED_DIRECTIONS` со списком кодов через запятую. Пустое значение означает
набор из четырёх направлений.
