# Слой API

Все эндпоинты живут под `/api/v1`. Префикс задаёт константа `API_PREFIX` в
`app/main.py`. Проверка здоровья `GET /healthz` стоит вне префикса: её читает
Docker и балансировщик, а не фронт.

## Роутеры по областям

Каталог `app/api/` держит по модулю на область экрана: `meta`, `predictions`,
`facilities`, `orders`, `metrics`, `dashboard`. Список `ROUTERS` в
`app/api/__init__.py` собирает их, а `app/main.py` монтирует под префиксом.

Добавить область — значит добавить модуль и строку в `ROUTERS`.

## Идентификатор запроса

Каждый ответ несёт заголовок `X-Request-Id`. Каждая строка лога несёт поле
`requestId`. По нему запрос собирается из логов целиком.

Идентификатор берётся из заголовка запроса, когда клиент его прислал. Так
запрос прослеживается через nginx и через фронт. Иначе сервер создаёт свой.

Значение живёт в `ContextVar` в `app/request_context.py`. Форматтер лога читает
его сам, поэтому передавать идентификатор через аргументы не нужно.

## Строка доступа

Промежуточный слой пишет одну строку на запрос: метод, путь, код ответа и
длительность в миллисекундах.

Собственная строка доступа uvicorn выключена флагом `--no-access-log` в
`Dockerfile.api`. Иначе в одном потоке идут два формата: наш JSON и обычный
текст uvicorn.

## Ошибки

Тело ответа при ошибке — всегда `{"detail": "..."}`. Коды: 400, 404, 409, 422.

Фронт тело не читает. Любой код от 400 и выше он показывает как ошибку с
кнопкой повтора. Текст нужен человеку при отладке, поэтому он должен быть
осмысленным.

Необработанное исключение даёт 500 с общим текстом. Трассировка уходит в лог
вместе с `requestId`, а клиенту не отдаётся: внутренности сервиса наружу не
уходят. Обработчик стоит в `app/errors.py`.

## Эндпоинты чтения

Восемь ручек: журнал прогнозов, карточка, таймсерии, точки карты, трассы,
объект, список заявок, заявка.

### Решения, принятые при реализации

**Одна точка на объект даёт `DISTINCT ON`.** Когда у объекта несколько
прогнозов, карта показывает самый вероятный. `DISTINCT ON (facility.id)` с
сортировкой по убыванию вероятности решает это одним запросом, без группировки
и без второго обращения к базе.

**Заявка на прогноз ищется скалярным подзапросом.** Поле `orderId` в прогнозе
нужно журналу. Подзапрос дешевле join с группировкой, потому что заявка на
прогноз одна.

**Границы `bbox` включительны.** Точка ровно на краю экрана обязана попасть в
ответ. Битый `bbox` не ошибка: карта получает всё, а не пустой экран.

**Неизвестное поле в `sort` не ошибка.** Фронт получает список в порядке по
умолчанию. Ошибка здесь означала бы пустой экран из-за опечатки в адресе.

**Границы дня считаются временем, а не строкой.** Колонки времени в PostgreSQL
не сравниваются со строкой. Фильтр по одной дате возвращает всё, что посчитано
в этот день, до 23:59:59.999.

**Битый блок карточки пропускается.** Разбор `blocks` из JSONB не роняет
карточку: направление `UNAUTHORIZED_ACCESS` отдаёт мусор намеренно, и это
проверка терпимости фронта, а не дефект.

**Повторяемые параметры объявлены как `Query(default_factory=list)`.**
Спецификация писала `Query(default=[])`. Изменяемое значение по умолчанию
ловит линтер, а поведение то же самое.

### Данные для проверки

Реальных выгрузок нет, поэтому ручки проверяются фикстурой `tests/conftest.py`.
Фикстура не изображает данные Москоллектора. Она закрывает ветви кода: каждый
уровень риска, каждый статус обеих сущностей, объект с двумя прогнозами,
направление с битыми блоками и заявка с записанным итогом.

Генератор сырья с заложенными зависимостями остаётся на задачу 10. До прихода
выгрузок он проверял бы модель, которой нет, на данных, которых нет.

## Действия диспетчера

Два эндпоинта: `POST /predictions/{id}/actions/{code}` и
`POST /orders/{id}/actions/{code}`. Тело — плоский объект значений формы. Ответ
— обновлённая сущность целиком, чтобы фронт положил её в кэш без второго
запроса. Отдельных ручек под кнопки нет.

### Таблица переходов

Файл `app/domain/transitions.py` держит переходы данными, а не ветвлением по
коду. Роутер ищет запись по коду и статусу.

| Сущность | Код | Из | В | Эффект |
|---|---|---|---|---|
| Прогноз | `confirm_order` | `NEW`, `IN_REVIEW` | `ORDER_CONFIRMED` | заявка `AUTO_CREATED` → `CONFIRMED` |
| Прогноз | `inspect` | `NEW`, `IN_REVIEW` | `IN_REVIEW` | нет |
| Прогноз | `reject` | `NEW`, `IN_REVIEW`, `ORDER_CONFIRMED` | `REJECTED` | открытая заявка → `REJECTED` |
| Заявка | `confirm` | `AUTO_CREATED` | `CONFIRMED` | нет |
| Заявка | `reject` | `AUTO_CREATED` | `REJECTED` | нет |
| Заявка | `start` | `CONFIRMED` | `IN_PROGRESS` | нет |
| Заявка | `close` | `IN_PROGRESS` | `DONE` | пишет `outcome`, прогноз → `CLOSED` |

Добавить действие — значит добавить запись сюда и в `app/domain/actions.py`.

### Решения

**Тело проверяется описанием формы.** Проверку ведёт тот же список `fields`,
которым фронт рисовал форму. Источник правды один: правка поля меняет и форму,
и проверку. Отказ — 422 с указанием поля.

**`predictionConfirmed` принимает только `true` или `false`.** Строка `"true"`
даёт 422. Моки фронта приводят чужой тип к `false`, а сервер отказывает. Обе
стороны выполняют требование «строка не считается подтверждением», но отказ
честнее: молча записанное `false` испортило бы Recall.

**Недопустимое в текущем статусе действие даёт 409.** Сущность есть, тело
верное, но переход запрещён. Текст называет текущий статус и доступные коды.
Моки статус не проверяют вовсе. Фронт присылает только те коды, что пришли в
`actions`, поэтому строгость сервера его не ломает, а закрытие уже закрытой
заявки испортило бы метрики.

**Неизвестный код над прогнозом переводит его в `IN_REVIEW`.** Поведение взято
из моков. Над заявкой тот же случай оставляет статус без изменений, тоже по
мокам. Асимметрия унаследована, а не придумана.

**Смена статуса идёт с условием по прежнему значению.** Два диспетчера могут
нажать кнопку одновременно. Если строка не обновилась, ответ 409, а не тихая
потеря одного из действий.

**Одна транзакция на действие.** Зависимость `get_tx` в `app/db.py` коммитит на
выходе и откатывает на ошибке. Действие меняет две сущности сразу, поэтому
половинчатый перевод недопустим. Отказанное действие не пишет в `action_log`.

**Аудит хранит тело целиком.** Таблица `action_log` — единственный след того,
что ввёл диспетчер.
