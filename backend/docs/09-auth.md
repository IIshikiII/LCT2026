# Вход в систему, роли и учётные записи

Зачем сделано так — [ADR 0007](../../docs/adr/backend/0007-roles-and-auth.md). Здесь порядок
работы: как войти, как завести запись, что отвечает сервер.

## Роли

| Роль | Код | Видит | Может |
|---|---|---|---|
| Техник | `TECHNICIAN` | один комплекс | читать |
| Диспетчер района | `DISTRICT_DISPATCHER` | комплексы своего района | брать в работу, решать, назначать бригаду, отклонять заявку |
| Диспетчер ОДС | `ODS_DISPATCHER` | всё предприятие | то же на всём предприятии |
| Группа реагирования | `RESPONSE_TEAM` | всё предприятие | закрывать заявку отметкой о факте |

Состав ролей назвал заказчик на QA-сессии. Делить права по
инженерным системам он не советует: тенденции нужны всем.

## Вход

Вход идёт двумя запросами.

1. `POST /api/v1/auth/login` с телом `{"username": "...", "password": "..."}`.
   Ответ несёт `status` и `mfaToken`. Токена сессии здесь нет.
2. `POST /api/v1/auth/mfa` с телом `{"mfaToken": "...", "code": "123456"}`.
   Ответ несёт `accessToken`, срок в секундах и данные пользователя.

Поле `status` первого ответа принимает два значения.

| Значение | Что делать |
|---|---|
| `MFA_REQUIRED` | взять код из аутентификатора и послать второй запрос |
| `ENROLL_REQUIRED` | завести ключ по полям `secret` и `otpauthUrl`, потом послать второй запрос |

Токен идёт в заголовке `Authorization: Bearer <токен>`. Срок задаёт переменная
`AUTH_TOKEN_TTL_MINUTES`, по умолчанию 480 минут.

### Регистрация ключа

Сервер создаёт секрет и отдаёт его **один раз**. В базу секрет попадает только
после верного кода. Если код не подошёл, запись остаётся без ключа, и следующий
вход начнёт регистрацию заново.

Формат стандартный: HMAC-SHA1, шаг 30 секунд, шесть цифр. Подходит любой
аутентификатор, в том числе настольный: ключ живёт в приложении, а не в
телефоне.

Проверены Яндекс Ключ, Google Authenticator, Microsoft Authenticator,
1Password, Bitwarden, Aegis и KeePassXC.

Завести ключ можно тремя способами, по убыванию удобства.

1. Навести камеру аутентификатора на QR-код. Интерфейс рисует его из той же
   ссылки `otpauth://`.
2. Открыть ссылку `otpauth://` с самого телефона: приложение заведёт запись.
3. Ввести строку `secret` руками.

Имя системы в ссылке латинское, `ARM ODS`, и это не небрежность. Кириллица
кодируется по шесть знаков на букву и удлиняет ссылку со 121 знака до 181.
QR вырастает с 45 модулей до 57, и телефон берёт его с экрана заметно хуже.

## Открытые маршруты

Токена не требуют шесть адресов: `/healthz`, `/api/v1/auth/login`,
`/api/v1/auth/mfa`, `/api/v1/docs`, `/api/v1/docs/oauth2-redirect`,
`/api/v1/openapi.json`. Список лежит в `app/api/__init__.py`, тест
`tests/test_auth_guard.py` следит, чтобы ни один другой маршрут не остался без
проверки.

## Коды ответа

| Код | Когда |
|---|---|
| 401 | токена нет, токен негоден, срок истёк, учётная запись отключена |
| 403 | токен верный, но роль не выполняет это действие |
| 404 | объект существует, но лежит вне области видимости роли |

Ответ 404 вместо 403 на чужой прогноз выбран намеренно: разные коды сказали бы,
что прогноз с таким номером есть.

## Учётные записи

### Демонстрационные

Команда `python -m app.cli seed` заводит четыре записи, по одной на роль:
`ods`, `district`, `tech`, `crew`. Пароль у всех один и приходит из переменной
`SEED_PASSWORD`, по умолчанию `collector`.

Второй фактор у них не заведён. Первый вход каждой роли проходит регистрацию
ключа целиком, и проверяющий видит весь путь.

Границы видимости берутся из данных посева: техник получает первый коллектор,
диспетчер района — район этого коллектора.

### Наборы тестового стенда

Ключ второго фактора остаётся в том приложении-аутентификаторе, где его
завели, поэтому один набор на всех не годится: первый же проверяющий заведёт
ключ у себя. Учётные записи живут наборами по четыре роли, и номер набора лежит
в колонке `demo_set`.

Первый набор создаёт `seed`. Следующие заводит панель на экране входа, она же
удаляет ненужные. Логины набора получают номер: `ods-2`, `district-2` и так
далее.

Панель появляется при переменной `TEST_STAND`. Без неё список приходит пустым,
а создание и удаление отвечают 404.

```
TEST_STAND=true docker compose up -d api
```

**Флаг раздаёт логины и пароли без входа в систему.** Так и задумано: панель
рисуется на экране входа. В промышленной установке он обязан быть выключен.

Три эндпоинта под панелью:

```
GET    /api/v1/auth/test-accounts         список наборов
POST   /api/v1/auth/test-accounts         завести следующий
DELETE /api/v1/auth/test-accounts/{номер} удалить набор целиком
```

Настоящие записи панель не видит и не удаляет: у них `demo_set` пустой.

### Свои

```
python -m app.cli create-user --username ivanov --full-name "Иванов И. И." \
  --role DISTRICT_DISPATCHER --scope CAO --password "..."
```

Вид области видимости берётся у роли, а не у команды: техник не может получить
всё предприятие по недосмотру. Параметр `--scope` называет только значение.
Повторный вызов с тем же логином обновляет запись.

## Переменные окружения

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `AUTH_SECRET` | случайный на запуск | ключ подписи токенов |
| `AUTH_TOKEN_TTL_MINUTES` | `480` | срок токена сессии |
| `AUTH_MFA_TTL_SECONDS` | `300` | срок промежуточного токена |
| `SEED_PASSWORD` | `collector` | пароль записей команды `seed` |
| `TEST_STAND` | выключен | панель тестовых учёток на экране входа |

Переменная `AUTH_SECRET` не названа значит ключ создаётся случайным на этот
запуск, и перезапуск сервера снимает все сессии. На стенде это удобно, в
промышленной установке переменную задают.

## Журнал действий

Таблица `action_log` держит вход, выход, отказ во входе и каждое действие над
прогнозом и заявкой. Поле `entity_type` принимает `auth`, `prediction` или
`order`, поле `actor` — имя из токена.

Чтения в таблицу не пишутся: экран опрашивает сервер раз в минуту, и за смену
это тысячи строк на человека. Каждый запрос попадает в журнал доступа строкой
JSON с полями `method`, `path`, `status`, `durationMs` и `actor`.

Выборка «что делал человек за смену» идёт по индексу
`action_log (actor, created_at DESC)`.

## Обслуживание стенда

Две команды, которые нужны между проверяющими.

```
python -m app.cli reset-demo          # прогнозы снова новые, заявки в начале
python -m app.cli reset-keys          # снять ключи второго фактора у всех наборов
python -m app.cli reset-keys --set 2  # то же у одного набора
```

Сброс данных не трогает сами прогнозы, объекты и замеры моделей: он снимает
следы работы диспетчеров и бригад. Заявки конвейера возвращаются в
`AUTO_CREATED`, заявки диспетчера исчезают вместе с решением, которое их
породило. Записи журнала действий по прогнозам и заявкам удаляются, входы
остаются.

Сброс ключей нужен, когда приложение проверяющего ушло вместе с проверяющим.
Следующий вход начнёт регистрацию заново.
