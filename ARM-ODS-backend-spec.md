# Спецификация бэкенда АРМ диспетчера ОДС (LCT2026, задача 8)

Документ для LLM, которая будет писать `backend/`. Схем и картинок нет намеренно:
только текст, который влияет на решения. Источник истины по контракту API —
`frontend/docs/02-api-contract.md` и `frontend/src/shared/api/schemas.ts`;
этот файл описывает, чем контракт наполняется со стороны сервера.

## 1. Что делает бэкенд

1. Принимает исторические выгрузки СМВУ (csv: журнал значений за 7,5 года,
   справочник объектов, справочник каналов датчиков), нормализует их в
   реляционную схему.
2. Раз в N минут (по умолчанию 15) отдельным процессом по расписанию прогоняет
   конвейер прогнозирования по всем единицам прогноза и всем включённым
   направлениям, складывает прогнозы в БД.
3. Автоматически формирует заявки на превентивное обслуживание для прогнозов
   выше порога направления.
4. Отдаёт REST API, полностью совпадающий по формам с моками фронтенда.
5. Считает и отдаёт метрики качества (Precision/Recall) и здоровье конвейера.

Требования ТЗ, которые бэкенд обязан подтверждать данными: горизонт ≥ 24 ч,
время формирования прогноза < 5 мин (`computeMs` на прогноз и `lastRunMs` на
прогон), задержка обработки потока < 5 мин.

Precision и Recall в этот список не входят. ТЗ §9 требует вывести их из
качества данных, и заказчик подтвердил это на QA-сессии: 0,7 и 0,5 являются
значениями по умолчанию, администратор их правит, команда ставит свои с
обоснованием. Цель хранится на направление, а не одним числом на сервис. То же
относится к горизонту в 24 часа.

Сервис разделён на процессы с разными наборами зависимостей: `api` (только
читает готовые прогнозы и пишет действия диспетчера), `pipeline` (считает
прогнозы по расписанию), `ingest` (разовый разбор выгрузок), `mlflow` (реестр
версий моделей). Падение или уязвимость в трёх последних не затрагивает
процесс, слушающий порт. См. §2.

Чего бэкенд не принимает и почему. Журнал ОДС, реестр оборудования, историю
ремонтов, допуски АРМ-Контроль и графики ТО/ППР заказчик не передаст. Историю
ремонтов в компании не ведут вовсе, учётную систему по оборудованию сузили до
датчиков намеренно. Разбор лежит в `qa-session-answers.md` §1.5 и §1.6.

## 2. Стек

Это коммунальная инфраструктура: сервис переживёт хакатон и будет
поддерживаться людьми, которые его не писали. Отсюда два жёстких требования к
зависимостям, которые важнее удобства разработки.

**Правило числа.** Прямых зависимостей у процесса, работающего постоянно, —
не больше пяти. Каждая новая строка в `pyproject.toml` — это чужой код в
периметре, чей CVE придётся отслеживать и чью замену придётся искать, когда
автор забросит проект. Библиотека берётся, только если её отсутствие означает
больше сотни строк собственного кода или самописную криптографию, разбор
формата, парсинг протокола. Всё, что заменяется двадцатью строками на stdlib,
пишется на stdlib.

**Правило разделения.** Зависимости делятся на непересекающиеся наборы, и
образ API не содержит ничего из остальных. Уязвимость в парсере xlsx не
должна быть уязвимостью сервиса, слушающего порт.

### Набор `api` — постоянно работающий процесс, 5 прямых зависимостей

- Python 3.12 (stdlib: `logging`, `json`, `datetime`, `os`, `pathlib`,
  `dataclasses`, `zoneinfo` — этого хватает на конфиг, логи и время).
- `fastapi` — маршрутизация, валидация запросов, OpenAPI.
- `uvicorn` — ASGI-сервер. Ставить голым, **без экстры `[standard]`**: она
  тянет uvloop, httptools, watchfiles, python-multipart и email-validator,
  ни одно из которых здесь не нужно. По той же причине не ставить
  `fastapi[standard]`.
- `pydantic` (v2) — DTO ответов. Приходит транзитивно с fastapi, но
  используется напрямую, поэтому объявляется явно.
- `sqlalchemy` (2.x, только Core, без ORM) — построение запросов с
  параметризацией. ORM не берём: ленивые загрузки и сессии — главный источник
  неочевидных багов у поддерживающего персонала, а запросы здесь простые и
  наперечёт.
- `psycopg` (v3) — драйвер PostgreSQL.

Транзитивно приезжают только `starlette`, `anyio`, `sniffio`,
`typing-extensions`, `pydantic-core`, `click`, `h11`. Дерево целиком должно
помещаться на экран: `uv tree` — часть ревью, а не любопытство.

Чего в этом наборе нет и почему:

- `pydantic-settings` — не нужен. Конфиг это `os.environ` и один
  `@dataclass(frozen=True)` в `app/config.py`, тридцать строк.
- `alembic` — не нужен. Миграции — нумерованные `.sql` файлы в
  `backend/migrations/` и запускалка на тридцать строк, которая держит
  применённые версии в таблице `schema_migration`. Alembic тянет Mako
  (шаблонизатор с исполнением кода) ради генерации файлов, которые здесь
  пишутся руками и читаются глазами дежурного. Простой SQL к тому же
  единственный формат миграции, который сможет применить DBA без Python.
- `APScheduler` — не нужен и вреден. Планировщик внутри веб-процесса означает,
  что при двух воркерах конвейер запускается дважды, а при падении API
  прогнозы перестают считаться молча. Запуск конвейера — отдельный процесс
  `python -m app.cli run-pipeline`, вызываемый системным `cron` или
  `systemd`-таймером. Это ноль зависимостей, отдельный лог и понятный
  дежурному способ запустить прогон руками.
- `structlog` — не нужен. JSON-логи это подкласс `logging.Formatter` на
  пятнадцать строк.
- Celery, брокер, Redis — не нужны: очереди в задаче нет, есть периодический
  батч.
- PostGIS — не нужен. Фильтр `bbox` карты это `WHERE lon BETWEEN %s AND %s AND
  lat BETWEEN %s AND %s` с обычным составным индексом. Расширение PostGIS —
  это большой кусок C в адресном пространстве СУБД ради того, чего мы не
  делаем: проекций, пересечений, буферов.
- TimescaleDB — не нужен. Объёмы (миллионы строк, не миллиарды) закрываются
  штатным декларативным партиционированием PostgreSQL по месяцу и BRIN-индексом
  по времени.

### Набор `ml` — процесс конвейера, запускается по расписанию

- `scikit-learn` (BSD) — калибровка вероятностей, метрики, разбиение по
  времени. Приносит `numpy`, `scipy`, `joblib`, `threadpoolctl`; `joblib`
  используется для сериализации моделей и отдельной зависимостью не является.
- `lightgbm` (MIT) — модель направления. Переехала из набора `research` после
  замера, см. ниже.
- `shap` (MIT) — вклады признаков для `explain()`. Их считает тот же процесс,
  что и прогноз.

Бустинг из отдельной библиотеки попадает в этот набор **только** после замера
на отложенной выборке, показавшего осмысленный выигрыш, и с записью замера в
`backend/docs/`. Переезжает одна библиотека, а не три: каждая тянет свой
скомпилированный бинарник и OpenMP-рантайм, что усложняет и сборку образа, и
обновление при уязвимости. Три бустинга в одном конвейере — это три способа
получить разный результат и ни одного объяснения. Сравнивать их между собой
— работа набора `research`, см. ниже.

Переезд состоялся. LightGBM обогнал наивную планку на отложенной выборке
направления «несанкционированный доступ»: точность 21,05 % против 11,32 % при
той же полноте. Замер лежит в `ml/access/out/metrics.json`, ключ
`test.beats_naive`, процедура переезда — в `backend/docs/01-dependencies.md`.
Библиотека `shap` приехала вместе с ним: объяснение прогноза обязательно (§7),
и считать его отдельным процессом незачем. Проигравшие бустинги `catboost` и
`xgboost` остались в наборе `research`.

### Набор `ingest` — разовый разбор выгрузок, в проде не установлен

- `openpyxl` (MIT) — чтение `.xlsx`. Единственный способ не писать разбор
  OOXML руками.

`pandas` и `polars` в наборах сервиса не стоят. Разбор выгрузки — это проход по
строкам листа с записью в PostgreSQL пачками через `psycopg.copy`; датафрейм в
этом сценарии не даёт ничего, кроме ста мегабайт зависимостей и соблазна
держать всю выгрузку в памяти. Агрегации, ради которых обычно берут pandas,
считает SQL — быстрее и без выгрузки данных из СУБД. Если внутри `ml` для
подготовки признаков окажется нужен датафрейм — это `numpy`, уже пришедший со
scikit-learn. Разведочный анализ живёт в наборе `research`, где pandas стоит.

### Набор `mlflow` — реестр моделей, отдельный сервис

- `mlflow` (Apache-2.0) — трекинг обучения и реестр версий моделей.

Команда ведёт версии моделей через MLflow, поэтому он входит в периметр. Он
нарушил бы правило числа, если бы стоял в наборе `api`, поэтому он выделен в
четвёртый набор. Правило разделения соблюдается: образ `api` не содержит
`mlflow`, а образ `pipeline` содержит только клиентскую часть.

Как это устроено:

1. Сервис `mlflow` в `docker-compose.yml` держит веб-интерфейс на порту 5000.
2. Хранилище трекинга — тот же PostgreSQL, отдельная база `mlflow`.
3. Артефакты моделей лежат в томе `backend/artifacts/`.
4. Процесс `pipeline` обращается к серверу по `MLFLOW_TRACKING_URI`.
5. Модуль `app/ml/tracking.py` закрывает MLflow двумя функциями: `log_run` и
   `load_model`. Никакой другой модуль не импортирует `mlflow`.

Пункт 5 обязателен. Он даёт замену реестра одним файлом и держит конвейер
работоспособным, когда сервер трекинга недоступен.

### Набор `research` — разведочный анализ, ни в один образ не входит

- `pandas`, `matplotlib`, `seaborn`, `jupyterlab` — датафрейм, графики, тетради.
- `catboost` (Apache-2.0), `lightgbm` (MIT), `xgboost` (Apache-2.0) — сравнение
  моделей на отложенной выборке.

Команда ведёт разведочный анализ, подбор модели и кросс-валидацию сама.
Правило числа считает зависимости постоянно работающего процесса, поэтому этот
набор его не нарушает. Правило разделения соблюдается: `Dockerfile.research`
поднимает JupyterLab отдельным сервисом, и ни `api`, ни `pipeline` из него
ничего не наследуют.

Граница проходит так: в `research` библиотеки сравнивают, в `ml` работает
победитель. Перенос стоит одного замера на отложенной выборке и записи о нём в
`backend/docs/01-dependencies.md`.

### Инструменты разработки (в образы не попадают)

- `uv` — установка и lock-файл.
- `ruff` — линт и формат (заменяет связку flake8 + isort + black одним бинарём).
- `pytest` — тесты. Асинхронные тесты не писать: `fastapi.testclient.TestClient`
  синхронный, поэтому `pytest-asyncio` не нужен; `httpx` приезжает
  транзитивно с TestClient.
- `mypy` в нестрогом режиме — опционально.
- Docker + docker compose: сервисы `api`, `db`, `pipeline`. Тестовая БД — тот же
  `db` с отдельным именем базы; `testcontainers` не нужен.

### Порядок обращения с зависимостями

1. Версии фиксируются lock-файлом, образ собирается только из него.
2. Новая зависимость добавляется отдельным коммитом, в описании которого сказано:
   какую задачу закрывает, сколько строк своего кода заменяет, какая лицензия,
   когда был последний релиз, сколько тянет транзитивно.
3. Перед защитой и перед каждым релизом — `uv pip audit` (или `pip-audit`)
   по lock-файлу; результат прикладывается к релизу.
4. Лицензии — только MIT / BSD / Apache-2.0. GPL, AGPL, LGPL со статической
   линковкой, «source-available» (BSL, SSPL, Elastic) и любые SaaS-зависимости
   запрещены: сервис передаётся эксплуатирующей организации.

Чего не брать сверх перечисленного: Django (тяжёл для REST-only), Flask (нет
валидации из коробки), MongoDB (данные реляционные), Kafka (нет потока),
ORM-надстройки над SQLAlchemy, ORM-миграторы, обвязки над логированием,
клиенты облачных сервисов.

## 4. Контракт API — что реализовать буквально

База `/api/v1`. Списки отдаются конвертом `{ items, page, pageSize, total }`.
Четыре эндпоинта конверт не используют, и это намеренно: `/facilities` и
`/facilities/lines` отдают GeoJSON, `/metrics/models` и `/dashboard/top-risks`
отдают голый массив.

- `POST /auth/login` (открыт)
- `POST /auth/mfa` (открыт)
- `GET  /auth/me`
- `POST /auth/logout`
- `GET  /meta`
- `GET  /predictions?direction&level&status&complex&assignee&from&to&sort&page&pageSize`
- `GET  /predictions/{id}`
- `GET  /predictions/{id}/timeseries`
- `POST /predictions/{id}/actions/{code}`
- `GET  /facilities?bbox&direction&level&complex` (GeoJSON FeatureCollection)
- `GET  /facilities/lines` (GeoJSON FeatureCollection трасс коллекторов)
- `GET  /facilities/{id}`
- `GET  /orders?status&dueBefore&sort&page&pageSize`
- `GET  /orders/{id}`
- `POST /orders/{id}/actions/{code}`
- `GET  /metrics/models`
- `GET  /metrics/pipeline`
- `GET  /dashboard/summary`
- `GET  /dashboard/top-risks?limit=10`

Токен обязателен везде, кроме двух шагов входа, проверки здоровья и трёх
адресов описания API. Список открытых маршрутов лежит в `app/api/__init__.py`,
и тест `tests/test_auth_guard.py` следит, чтобы ни один другой не остался без
проверки. Разбор — §10 и ADR 0007.

Трассы коллекторов отдаёт отдельный эндпоинт `/facilities/lines`. Причина:
карта опрашивает точки раз в минуту, а трассы не меняются. Фронт берёт их один
раз за сессию.

Эндпоинт `/predictions/{id}/timeseries` параметров не принимает. Окно выбирает
сервер.

Правила параметров: `direction`, `level`, `status` — повторяемые
(`?direction=A&direction=B`), это мультивыбор, в FastAPI — `Query(default=[])`.
`sort` — строка `field:asc` / `field:desc`, поля белым списком.
`bbox` — `minLon,minLat,maxLon,maxLat`.

Белый список полей сортировки. Ключи совпадают с ключами колонок, поэтому
заголовок таблицы сортирует то, что показывает.

- Прогнозы: `computedAt`, `probability`, `horizon`, `direction`, `status`,
  `facility` (по адресу), `summary`, `risk` (по вероятности).
- Заявки: `number`, `dueAt`, `orderStatus`, `workType`, `facility` (по адресу).

Неизвестное поле в `sort` — не ошибка. Сервер его пропускает и отдаёт список в
порядке по умолчанию.
Все временные метки — ISO-8601 UTC со сдвигом (`2026-09-09T12:00:00Z`).
Ключи полей — camelCase (фронт ждёт именно их): в pydantic-моделях
`alias_generator=to_camel`, `populate_by_name=True`, ответы через
`model_dump(by_alias=True)`.

### Формы ответов

Повторяют `frontend/src/shared/api/schemas.ts` поле в поле. Кратко:

- `AppMeta`: `directions[{code,label,shortLabel,accent,minHorizonHours}]`,
  `riskLevels[{code,label,colorVar,order}]`,
  `statuses[{code,label,scope,colorVar?,terminal?}]` (`scope` = `prediction` |
  `order`),
  `complexes[{code,label}]` (16 штук, приходят из `facility_tree`, а не из
  кода), `journalColumns[str]`, `orderColumns[str]`,
  `dashboardWidgets[str]`, `reasons: {ключ -> [{code,label}]}`.
- `FacilityRef`: `id, complex, object, picket, offsetM?, distanceM, label,
  lat, lon`. Единица прогноза это пара «объект и пикет», см. §6.
- `Prediction`: `id, direction, level, probability (0..1), horizonHours,
  computedAt, computeMs, status, facility, summary, orderId?, assignee?,
  verdict?, dispatcherLevel?, decidedAt?`. Последние четыре поля держат решение
  диспетчера, разбор — ADR 0006.
- `PredictionDetail` = `Prediction` + `blocks[CardBlock]` + `actions[ActionDef]`.
- `CardBlock`: `{ type, title, data }`, где `data` — произвольный JSON.
- `ActionDef`: `{ code, label, kind, confirm?, fields[FieldDef] }`;
  `FieldDef`: `{ name, label, type, required?, minLength?, optionsRef?,
  placeholder?, help? }`. `optionsRef` указывает на ключ в `meta.reasons`.
- `WorkOrder`: `id, number, predictionId, facility, workType, dueAt, status,
  createdAt, createdBy, actions[], outcome?`;
  `outcome`: `{ actualCause, factConfirmed, comment, closedAt }`.
  Поле `createdBy` принимает `PIPELINE` или `DISPATCHER`: это происхождение
  заявки, а не состояние, поэтому оно поле, а не статус.
- `CurrentUser`: `username, fullName, role, roleLabel, scopeKind, scopeValue?,
  permissions[]`. Подпись роли приходит с сервера: списка ролей интерфейс не
  держит, как не держит списка направлений.
- `LoginChallenge`: `status, mfaToken, secret?, otpauthUrl?`. Поле `status`
  принимает `MFA_REQUIRED` или `ENROLL_REQUIRED`; секрет приходит только во
  втором случае и только один раз.
- `SessionResponse`: `accessToken, tokenType, expiresIn, user`.
- `ModelMetric`: `{ direction, precision, recall, targetPrecision,
  targetRecall, evaluatedAt }`.
- `PipelineHealth`: `{ lastRunAt, lastRunMs, freshnessMinutes, maxComputeMs,
  minHorizonHours, targetComputeMs, targetHorizonHours }`.
- `DashboardSummary`: `{ byLevel, byDirection, byStatus, byOrderStatus, total }`,
  где первые четыре — словари `код -> число`, а не массивы фиксированной формы.
- Таймсерии: `{ series: [{ name, unit?, points: [{t, v}] }], markerAt? }`.
- `/facilities` — GeoJSON `FeatureCollection`; в `properties` каждой точки:
  `facilityId, level, direction, predictionId, probability, address, collector`.
  Последние два показывает всплывающая подсказка карты. Координаты — `[lon, lat]`
  в этом порядке.
- `/facilities/lines` — GeoJSON `FeatureCollection` из `LineString`; у каждой
  трассы свойство `collector` с названием.

Поля `colorVar` и `terminal` у статуса необязательны в схеме, но оба меняют
экран, поэтому сервер обязан их слать. `colorVar` красит точку в подписи
статуса. Брать имя токена из палитры состояний, а не из палитры риска: зелёный
из шкалы риска читается как «низкий риск», а не как «работа закончена».

| Токен | Значение | Коды сегодня |
|---|---|---|
| `--state-attention` | ждёт диспетчера | `NEW`, `AUTO_CREATED`, `CONFIRMED` |
| `--state-progress` | работа идёт | `IN_REVIEW`, `ORDER_OPEN`, `IN_PROGRESS` |
| `--state-done` | закончено | `DECIDED`, `CLOSED_CONFIRMED` |
| `--state-muted` | отброшено | `REJECTED`, `CLOSED_NOT_CONFIRMED` |

Признак `terminal: true` помечает статус, на котором работа закончилась. Фронт
перестаёт предупреждать о сроке. Ставить его на `DECIDED`, `REJECTED`,
`CLOSED_CONFIRMED` и `CLOSED_NOT_CONFIRMED`. Статус без `colorVar` получает
нейтральную подпись, статус без `terminal` считается открытым.

### Типы блоков карточки, которые фронт умеет рисовать

`factors` (`{items:[{label,weight,value?}]}`, weight в -1..1),
`timeseries` (`{series,markerAt}`), `timeline` (`{events:[{at,title,kind,note?}]}`),
`table` (`{columns:[{key,header,align?}],rows:[{}]}`),
`keyvalue` (`{items:[{label,value}]}`).
Любой другой `type` фронт рисует запасным `GenericBlock` и не падает — можно
отдавать экспериментальные блоки без согласования.

## 5. Правила, наследуемые от фронтенда — не нарушать

1. **`direction`, `level`, `status` — свободные строки.** Никаких enum'ов в
   ответах и никаких `if/elif` по коду направления в слое API. Направление —
   строка в БД плюс запись в реестре `app/meta/`. Добавление нового направления
   должно быть добавлением плагина и строки в `/meta`, без правок роутеров.
2. **Один эндпоинт действий.** `POST /{entity}/{id}/actions/{code}` с плоским
   телом из значений полей формы. Ответ — обновлённая сущность целиком.
   Отдельных ручек `/confirm`, `/reject`, `/close` не заводить.
3. **`actions` вычисляются сервером** от текущего статуса сущности и роли
   пользователя. Фронт кнопки не придумывает. Прогноз принимает `take`,
   `release` и `decide`; заявка принимает `assign`, `reject` и `close`.
   Действие `close` принадлежит заявке и доступно только группе реагирования
   (ADR 0007). Оно обязано принимать `outcome.factConfirmed`. Значение только
   булево: строка `"true"` подтверждением не считается. Поле отвечает на
   вопрос, наступил ли факт на объекте, и является вторым ярлыком для
   дообучения. См. `backend/docs/06-labels-and-metrics.md`.
4. **Состав UI приходит из `/meta`**: колонки журнала, виджеты дашборда,
   справочники причин. Менять состав экрана — значит менять `/meta`, а не фронт.
5. **Терпимость к неизвестному взаимна**: фронт разбирает ответы мягко, поэтому
   добавление поля в ответ безопасно, а переименование существующего — нет.
   Переименование поля = правка `schemas.ts` и мок-хендлера фронта в том же PR.

## 6. Модель данных (минимум)

Иерархия повторяет выгрузку: район, комплекс, объект, пикет, канал датчика.
Первые три уровня лежат в справочнике объектов, канал приходит со ссылкой на
объект в поле `ид_объект`, пикет разбирается из названия датчика.

- `facility` — **единица прогноза: пара «объект и пикет»**, 3 947 штук.
  Поля: объект, номер пикета, комплекс, район, координата вдоль трассы в
  метрах (`ПК × 10 + смещение`), `lat` и `lon` на синтетической трассе, тип.
  Пикет равен 10 метрам и является контейнером оборудования. Это определение
  заказчика, и оно же делает пикет правильной единицей: объект (78 штук) не
  отвечает требованию ТЗ §6 «локация оборудования», а канал (11 485 штук)
  слишком мелок для диспетчера.
- `facility_tree` — узлы дерева выше единицы прогноза: район, 16 комплексов,
  78 объектов. Поля: идентификатор, родитель, уровень, вид, подпись. Дерево
  даёт фильтры интерфейса и границы видимости ролей (§10).
- `sensor` — канал данных датчика: тип инженерной системы, тип датчика,
  название, привязка к `facility`, признак активности. 11 485 строк.
- `alarm_event` — сработка СМВУ: канал, время, текст значения, флаг тревоги.
  Основная таблица, миллионы строк: штатное декларативное партиционирование
  PostgreSQL по месяцу плюс индекс `(sensor_id, occurred_at)`. Никаких
  расширений СУБД для этого не требуется. Полей `is_false` и `check_result` в
  источнике нет и не будет: журнал ОДС заказчик не передаст. Отметку диспетчера
  ставит наш собственный интерфейс при закрытии заявки.
- `sensor_reading` — показания датчиков: канал, `facility`, метрика (`metric`),
  время, значение, единица. Источник для `GET /predictions/{id}/timeseries` и
  для блока `timeseries` в карточке. Таблица `alarm_event` хранит дискретные
  события, поэтому графики карточки она не закрывает. Партиционирование по
  месяцу, как у `alarm_event`, плюс индекс `(facility_id, metric, observed_at)`.
- `event_type` — справочник текстов значения: текст, направление, уровень.
  16 значений из выгрузки. Направление события читается из таблицы, а не из
  `if` в коде, иначе новое значение потребует правки кода.
- `weather_hourly` — внешние факторы (температура, осадки) из открытых API
  метеослужб. ТЗ §13 называет их штатным источником, сценарий подтопления в
  ТЗ §12 на них опирается.

Таблиц `fault_log`, `repair`, `permit` и `inspection` в схеме нет. Источника
они не получат никогда, и это решение заказчика, а не задержка поставки.
Наработку на отказ насосов и вентиляторов разрешено брать усреднённой из
открытых источников, отдельной таблицы для этого не нужно.
- `prediction` — прогноз: направление, объект, вероятность, уровень, горизонт,
  `computed_at`, `compute_ms`, статус, `summary`, JSONB `blocks`, JSONB
  `features`, `model_version`. Колонка `blocks` — витрина для диспетчера,
  колонка `features` — вход модели, имя признака к числу. Решение диспетчера
  лежит четырьмя отдельными полями: `assignee`, `verdict`, `dispatcher_level`,
  `decided_at`. Статус отвечает за место в работе, поля — за то, что решил
  человек (ADR 0006).
- `work_order` — заявка: номер, прогноз, объект, тип работ, срок, статус,
  `created_by` со значением `PIPELINE` или `DISPATCHER`, `outcome` (JSONB) с
  `factConfirmed`.
- `app_user` — учётная запись: логин, имя, роль, вид и значение области
  видимости, хеш пароля, секрет второго фактора, источник записи (`LOCAL` или
  `LDAP`). Стоит на месте каталога Active Directory, которого заказчик не
  отдаст. Разбор — ADR 0007.
- `action_log` — аудит: кто, когда, какое действие, над чем, с каким телом.
  Поле `entity_type` принимает `prediction`, `order` или `auth`: ТЗ §11 требует
  журналировать все действия, и вход является первым из них.
- `pipeline_run` — прогон конвейера: начало, длительность, число прогнозов,
  версия моделей.
- `model_metric` — метрики по направлению и дате оценки.

Справочники `/meta` в схеме не лежат. Направления, уровни риска, статусы,
колонки, виджеты и списки причин держит реестр `app/meta/` в коде. Причина: они
меняются вместе с кодом роутеров и плагинов, а не вместе с данными, и
добавление направления не должно требовать миграции.

Исключение одно. Список комплексов приходит из данных, а не из кода: в выгрузке
их 16, и они меняются вместе с сетью. Ручка `/meta` отдаёт их из
`facility_tree`. Поле `facility.district` заменяется на `complex_id`: девяти
округов Москвы в данных нет, есть один район и 16 комплексов. Фильтр интерфейса
остаётся тем же по форме, меняется только наполнение.

Уровни риска считаются из вероятности порогами, задаваемыми на направление:
`LOW < 0.3 ≤ MEDIUM < 0.55 ≤ HIGH < 0.78 ≤ CRITICAL` это значения по умолчанию,
совпадающие с моками фронта. Свои границы направление называет полем
`Direction.level_thresholds`. Направление «несанкционированный доступ» держит
там 0.009438, 0.035251 и 0.04, потому что база события ниже процента и до общих
порогов оно не достаёт. Разбор — ADR 0004.

## 7. Конвейер прогнозирования

Один прогон: выбрать активные объекты → построить признаки на момент `now` →
для каждого направления вызвать его предиктор → откалибровать вероятность →
присвоить уровень → собрать `summary` и `blocks` → записать прогнозы одной
транзакцией → создать автозаявки → записать `pipeline_run`.

Запускается командой `python -m app.cli run-pipeline` из системного `cron` или
`systemd`-таймера, а не из веб-процесса. Одновременный запуск двух прогонов
исключается advisory-локом PostgreSQL (`pg_try_advisory_lock`), а не внешним
планировщиком: лок переживает перезапуск любого процесса и не требует ни одной
зависимости.

Требования:
- Горизонт каждого направления ≥ 24 ч, объявляется в `/meta`
  (`minHorizonHours`) и хранится в прогнозе (`horizonHours`).
- `compute_ms` измеряется на прогноз, `last_run_ms` на прогон; и то и другое
  обязано укладываться в 5 минут — это проверяемое требование ТЗ.
- Идемпотентность: повторный прогон в том же окне обновляет прогноз объекта, а
  не плодит дубли (уникальность `(facility_id, direction, computed_at_bucket)`).
- Прогноз без объяснения не публикуется: `blocks` обязаны содержать хотя бы
  `factors` (вклад признаков) и один `timeseries`, иначе диспетчер не может
  принять решение, а жюри — оценить модель.

Направления реализуются как плагины с единым протоколом: `code`,
`build_features(ctx)`, `predict(features) -> probability`,
`explain(features) -> blocks`,
`suggest_work_type(features, probability) -> str`,
`label_rule(conn, facility_id, window) -> bool`. Файл плагина лежит в
`app/ml/plugins/`, реестр `app/ml/registry.py` находит его сам. Добавление
направления не должно требовать правок конвейера.

Подпись, горизонт, типы работ и пороги заявки плагин не хранит. Их держит
реестр направлений `app/meta/`, и плагин связан с ним только кодом. Причина:
подпись направления нужна процессу `api`, который ни одной модели не видит.
Вторая копия подписи разошлась бы с реестром на первой же правке. Метод
`suggest_work_type` обязан вернуть строку из `work_types` своего направления.

Направление без плагина прогнозов не даёт, и это законное состояние. Реестр
отдаёт список таких направлений, а прогон пишет его в лог: пустой результат
обязан быть видимым решением, а не тихой пропажей.

Метод `label_rule` отвечает на один вопрос: наступило ли событие этого
направления на объекте в заданном окне времени. Он нужен обучению, а не
прогнозу.

Метод обязателен, потому что событие у каждого направления своё. Отказ датчика
ищется в журнале неисправностей, пожар — в сработках дымовых датчиков, доступ —
в сработках контактных датчиков без допуска, подтопление — в сработках датчиков
затопления и в работе насосов. Это разные факты в разных таблицах. Без
отдельного метода они попадут в общий код обучения ветвлением по коду
направления, что запрещает §5 правило 1.

Правило первого направления написано. Для «несанкционированного доступа»
событием является момент, а не строка: тревожный флаг на канале доступа в окне
24 часов после момента расчёта. Вывод и числа — в
`backend/docs/adr/0001-access-target.md`. У остальных трёх направлений
`label_rule` объявлен в протоколе и не реализован.

Замер прогона подтверждает границу ТЗ §9. Полный обход 3 947 единиц с одним
активным направлением идёт 35 255 мс против границы 300 000 мс, то есть с
запасом 8,5 раза. Прогон с четырьмя активными направлениями оценивается в 141
секунду. Первый замер дал 8,4 минуты: плагин читал модель с диска на каждую
единицу. Разбор и решение — в `backend/docs/adr/0003-pipeline-duration.md`.

Признаки берутся строго из данных с меткой времени до `computed_at`.

Работы делятся на два вида, и путать их нельзя. Плановое обслуживание,
проведённое до момента расчёта, — законный и сильный признак: оно возвращает
оборудование в исправное состояние и понижает вероятность события. Ремонт по
факту аварии — следствие события, а не его причина. Признак, который берёт
такой ремонт без ограничения по времени, научит модель тому, что ремонт
предсказывает аварию: метрики на отложенной выборке вырастут, а в работе модель
откажет.

Отдельно стоит признак от графика ТО и ППР: просрочка по регламенту. Он
считается из норматива и даты последнего обслуживания и не зависит от аварий
вовсе, поэтому протечь не может. Он работает даже тогда, когда записей о
фактически выполненной профилактике в выгрузках мало.

Вектор признаков, поданный модели, конвейер записывает в `prediction.features`.
Блок `factors` в `blocks` — витрина для диспетчера и источником данных не
является. См. `backend/docs/06-labels-and-metrics.md`.

## 8. Автоматические заявки

Правило по умолчанию: прогноз с уровнем HIGH или CRITICAL и без открытой заявки
на том же объекте по тому же направлению порождает `work_order` со статусом
`AUTO_CREATED`, сроком `dueAt = computed_at + horizonHours * коэффициент` (по
умолчанию 0.5) и типом работ от плагина направления. Пороги, коэффициент и
запрет дублей — в конфиге направления.

Жизненный цикл прогноза и заявки нарисован стрелками в
`ARM-ODS-lifecycle.md`, обоснование лежит в ADR 0006. Коротко.

Прогноз: `NEW → IN_REVIEW → DECIDED` либо `NEW → IN_REVIEW → ORDER_OPEN →
CLOSED_CONFIRMED | CLOSED_NOT_CONFIRMED`. Терминальны `DECIDED` и оба `CLOSED`.

Заявка: `AUTO_CREATED → CONFIRMED → IN_PROGRESS → CLOSED_CONFIRMED |
CLOSED_NOT_CONFIRMED`, ветка `REJECTED`. Заявку подтверждает решение диспетчера
по прогнозу, отдельного действия подтверждения нет.

Выезд назначает итоговый уровень `dispatcher_level`, а не согласие диспетчера с
моделью. Уровни `HIGH` и `CRITICAL` требуют выезда, `LOW` и `MEDIUM` закрывают
прогноз без заявки.

Названия статусов фронт берёт из `/meta`, менять их можно, но только вместе с
моками.

## 9. Метрики качества

`GET /metrics/models` отдаёт точность прогноза. Она считается по авариям из
данных: наступило ли событие в окне горизонта. Пока данных нет, отдаётся
офлайн-оценка на отложенной по времени выборке. Поле `evaluatedAt` показывает,
когда оценка получена, а `model_metric.method` — каким способом.

Отметка бригады `factConfirmed` в этот расчёт не входит. Она появляется только
после ввода сервиса в эксплуатацию и лежит на смещённой выборке: разметку
получают лишь прогнозы, по которым выехала бригада.
Recall по ней не считается вовсе, потому что среди закрытых заявок нет
пропущенных аварий. Разбор — в `backend/docs/06-labels-and-metrics.md`, план
использования — в `roadmap-post-deployment.md`.

Разбиение при обучении — только по времени (train на прошлом, test на будущем).
Случайный `train_test_split` на временных рядах даёт утечку и завышенные
Precision/Recall, что вскроется на защите.

Цель по качеству хранится на направление в полях `target_precision` и
`target_recall` и правится администратором. Общего числа на сервис нет. Причина
в данных: наивная планка «событие повторится завтра» лежит от 4,4 % у пожарного
риска до 39,7 % у риска подтопления. Одно число либо занизит сильные
направления, либо провалит пожар. Замер по направлениям лежит в
`hackathon-gap-analysis.md` §A4.

Наивная планка обязательна к публикации рядом с метрикой. Модель, которая её не
обгоняет, не нужна, и жюри проверяет именно это.

Первое направление замерено. Ниже отложенная выборка «несанкционированного
доступа»: 180 суток 2026 года, 1 281 единица, 1 755 проникновений.

| Счёт | Наивная планка | Модель на пороге 0,035251 |
|---|---|---|
| Точность клетки | 11,32 % | 18,4 % |
| Полнота клетки | 10,82 % | 12,6 % |
| Нарядов в сутки | 3,91 | 3,89 |
| Предупреждено проникновений | 129 из 1 755 | 215 из 1 755 |
| Нарядов на одно предупреждение | 5,45 | 3,26 |

PR-AUC равна 0,0745 при базе 0,944 %. Порог выведен из цены ошибки для
диспетчера, а не из круглого числа: он держит день диспетчера неизменным и при
этом предупреждает в 1,67 раза больше проникновений. Обоснование — в
`backend/docs/adr/0002-access-threshold.md`.

Числа §A4 разбора на эту выборку не переносятся. Там замер сделан на
канало-днях, здесь на паре «объект и пикет» по часам. Сверка обеих единиц лежит
в `backend/docs/adr/0001-access-target.md`.

Вероятность модели пока не откалибрована: в нижней полосе она занижает риск в
1,6 раза, в верхней завышает вдвое. Поэтому граница уровня `CRITICAL` не
назначена, а порог читается как ранг, а не как шанс.

Из обучения исключается объект 5343 за 2020 и 2021 годы. В эти годы заказчик
внедрял новую версию системы мониторинга, две системы работали параллельно, и
объект дал 1 036 606 ложных записей «Неисправен». Это 73 % всех записей
«Неисправен» за 7,5 года. Исключается один объект за два года, а не годы
целиком.

## 10. Нефункциональные требования

- CORS для `http://localhost:5173`.
- OpenAPI отдаётся FastAPI автоматически, `/api/v1/docs`.
- Ошибки: JSON `{ "detail": ... }`, коды 400/404/409/422; фронт их переживает,
  но осмысленный текст нужен для отладки на защите.
- Логи в JSON, с `request_id`; каждый прогон конвейера логирует длительность.
  Формат даёт свой `logging.Formatter`, внешней библиотеки логирования нет.
- Миграции: `python -m app.cli migrate` применяет неприменённые файлы из
  `migrations/` по возрастанию номера в одной транзакции на файл и записывает
  версию в `schema_migration`. Откат — отдельным файлом `down`, автогенерации нет.
- Сиды: команда `python -m app.cli seed`, поднимающая демо-набор данных, чтобы
  фронт с `VITE_USE_MOCKS=false` заработал сразу после `docker compose up`.
- Здоровье: `GET /healthz` — проверка соединения с БД, без зависимостей.
- Аутентификация обязательна. ТЗ §11 держит RBAC и федерацию с LDAP/AD в
  обязательных требованиях, а не в §8 «по согласованию». Токен проверяется на
  каждом эндпоинте, кроме шести открытых. Проверка только на фронте правами не
  является.
- Журнал действий пишет имя пользователя из токена, а не константу. ТЗ §11
  требует журналировать все действия. Смена состояния и вход лежат в таблице
  `action_log`, чтение — строкой журнала доступа с полем `actor`.

### Роли

Заказчик свёл пять групп пользователей из ТЗ §3 к трём уровням видимости и
согласился на четвёртую роль для подтверждения факта на объекте (ответ 4.1).
Делить права по инженерным системам он не советует: тенденции нужны всем.

| Роль | Область видимости | Права |
|---|---|---|
| `TECHNICIAN` | один комплекс | чтение |
| `DISTRICT_DISPATCHER` | комплексы своего района | `take`, `release`, `decide`, `assign`, `reject` |
| `ODS_DISPATCHER` | всё предприятие | те же пять действий |
| `RESPONSE_TEAM` | всё предприятие | `close` |

Право названо кодом действия. Состав кнопок карточки считает сервер (§5 правило
3), поэтому отбор по правам идёт там же, где список действий и собирается.
Кнопка без права не доезжает до экрана, а запрос мимо интерфейса получает 403.

Область видимости режет выборку условием запроса к базе, а не в интерфейсе.
Прогноз вне границы отвечает 404, а не 403: разные коды сказали бы, что прогноз
с таким номером есть. Качество модели границей не режется: оно измерено на всей
сети.

Политика работы с одним прогнозом простая: видят все, запись остаётся за тем,
кто закрыл. Блокировка карточки за первым открывшим необязательна.

### Вход в систему

Вход идёт двумя шагами: пароль, затем одноразовый код по RFC 6238. Пароль без
кода сессии не открывает: промежуточный токен несёт поле `kind` и не принимается
ни одним эндпоинтом данных. Запись без заведённого ключа получает секрет один
раз, и в базу он попадает только после верного кода.

Пароль, код и токен написаны на стандартной библиотеке: `hashlib.scrypt`,
`hmac` и подпись HS256. Правило §2 о пяти прямых зависимостях набора `api`
осталось целым.

Таблица `app_user` стоит на месте каталога Active Directory: настоящий каталог
заказчик не отдаст (ответ 4.2), а место стыковки названо полем `directory` и
функцией `app/auth/directory.authenticate`.

Порядок работы описан в `backend/docs/09-auth.md`, обоснование — в ADR 0007.

## 11. Порядок работы

Тот же, что во фронтенде: сначала документация, потом тест, потом код. Правка

остаётся только для демонстрационного стенда.

Правило прежнее: и парсер выгрузки, и генератор пишут в те же таблицы. Модули
`features/`, `ml/` и `pipeline/` не знают, откуда пришла строка.

### Что даёт выгрузка

| Источник | Что в нём | Строк |
|---|---|---|
| журнал значений | канал, время, значение, флаг тревоги | 313 546 016 |
| справочник объектов | район, комплексы, объекты | 95 |

Форматов журнала два, и загрузчик обязан читать оба. Исторический пишет

### Что приходится имитировать и почему

Имитация здесь не костыль. Заказчик предложил её сам и назвал ожидаемым
решением, а ментор поставил одно условие: имитация не должна быть случайными
числами. Каждая заглушка обязана называть себя заглушкой в интерфейсе и в
сопроводительной документации.

| Что | Почему нет настоящего | Чем заменяем |
|---|---|---|
| поток СМВУ | интеграцию не дадут по требованиям безопасности | отдельный сервис проигрывает выгрузку как поток |
| решение диспетчера | журнал ОДС ведётся отдельно и интегрирован не будет | отметка в нашем интерфейсе при закрытии заявки |
| система учёта заявок | заказчик использует GLPI, доступа нет | заглушка с чтением статуса по внешнему идентификатору |
| координаты | московская система координат, пересчёт вне проекта | синтетическая трасса, длина из номеров пикетов |
| наработка на отказ | историю ремонтов не ведут вовсе | усреднённые значения из открытых источников |

### Синтетическая трасса

Заказчик разрешил линейные объекты прямо: достаточно осевой линии, `LineString`
или `MultiLineString`, и условных значков на ней.

Трасса строится не случайной ломаной. Длина берётся из данных: координата вдоль
линии равна `ПК × 10 + смещение`, пикет равен 10 метрам. Поэтому длина линии
настоящая, а положение на карте города условное. Объект `Кси ПК0-ПК202`
получает линию в 2 020 метров, а не произвольный отрезок.

Девять округов Москвы из прежних заглушек убираются. В данных один район и 16
комплексов.

### Степени готовности направлений

Направления заполнены неравномерно намеренно. Это проверка того, как фронтенд
переносит неполные и битые данные. Заглушки фронта её сохраняют и после
подключения сервера.

| Направление | Сырьё | Предиктор | Прогнозы |
|---|---|---|---|
| Несанкционированный доступ | полное | обученная модель LightGBM | полные, с объяснением по SHAP |
| Отказ датчика | полное | нет | нет ни одного |
| Пожарный риск | полное | нет | нет ни одного |
| Риск подтопления | есть, но направление выключено | нет | нет ни одного |

Строка «несанкционированный доступ» поменялась. Раньше это направление несло
битые прогнозы: пустые блоки, `null` в полях, неизвестный тип блока. Теперь оно
единственное доведённое до конца, от витрины до экрана диспетчера.

Отсюда два следствия, и оба надо закрыть до сдачи.

1. **Проверку на битые данные несёт другое направление.** Фронтенд обязан
   переносить пустой блок, `null` в поле и неизвестный тип блока. Заглушки
   фронта эту проверку держат, настоящий сервер её больше не даёт.
2. **Три направления остались без предиктора.** Направление без плагина
   прогнозов не даёт, и это законное состояние (§7). Молчать о нём нельзя:
   реестр отдаёт список таких направлений, а прогон пишет его в лог.

Направление «Риск подтопления» лежит в реестре выключенным. Оно служит
проверкой на гибкость: включение переменной `ENABLED_DIRECTIONS` обязано
провести его в фильтры, на карту и на дашборд без правок кода.

Здесь есть противоречие, и его надо разрешить до сдачи. По данным подтопление
предсказуемо лучше всех остальных: база 4,84 % и наивная точность 39,7 %
против 0,31 % и 4,4 % у пожара. ТЗ §6 и §12 называют подтопление прямо, а
заказчик дал по нему отдельный сценарий с разуклонкой и мигающим насосом.
Держать самое сильное направление выключенным ради теста на гибкость выглядит
неверно. Тест надо перевести на другое направление.

Направление «Износ инфраструктуры» из первоначальной постановки убрано.
Признаков для него выгрузка не даёт, а QA-сессия подтвердила, что историю
ремонтов в компании не ведут вовсе. Постановка разрешает взять подмножество
направлений.
