# LCT2026: прогноз аварий в коллекторах Москвы

Сервис считает вероятность аварии на участках инженерных коллекторов на
ближайшие сутки. Диспетчер ОДС видит риски на дашборде, на карте и в журнале.
Опасный прогноз сам создаёт заявку на превентивное обслуживание.

| Папка | Что в ней |
|---|---|
| `backend/` | REST API, конвейер прогноза, модуль заявок, вход и роли. FastAPI и Postgres в Docker |
| `frontend/` | Рабочее место диспетчера: дашборд, карта, журнал прогнозов, заявки |
| `ml/` | Модели по направлениям прогноза |
| `deploy/` | Установка на сервер Ubuntu 22.04 |

Стенд: <https://utility-monitor.ru>.

## Как работает сервис

1. **Данные.** Источник это журнал датчиков системы мониторинга СМВУ.
   Загрузчика выгрузки в сервисе пока нет. На стенде база получает синтетику
   с фиксированным семенем, поэтому каждый посев даёт те же объекты и события.
2. **Прогон конвейера.** Команда `run-pipeline` обходит все единицы прогноза.
   Для каждого активного направления она строит признаки строго до момента
   расчёта, считает вероятность и объясняет её вкладами признаков (SHAP).
3. **Уровень риска.** Вероятность получает уровень `LOW`, `MEDIUM`, `HIGH` или
   `CRITICAL`. Границы уровней задаёт направление.
4. **Заявка.** Прогноз уровня `HIGH` или `CRITICAL` создаёт заявку. Правила
   ниже.
5. **Решение человека.** Диспетчер берёт прогноз в работу и принимает решение.
   Бригада закрывает заявку и ставит отметку «факт подтверждён на объекте».
   Эта отметка потом даёт оценку модели на реальных данных.
6. **API.** Интерфейс читает всё через REST API `/api/v1`. Вход идёт в два
   шага: пароль, затем одноразовый код из приложения-аутентификатора.

Прогон задуман раз в 15 минут. Таймера пока нет, и прогон запускают командой.

Интерфейс не знает заранее, сколько направлений существует. Он получает их
список из `GET /meta`. Новое направление появляется в фильтрах, на карте и на
дашборде без правки кода интерфейса.

## Правила событий

### Что считается событием

Правило описано для направления «несанкционированный доступ». Только у него
есть обученная модель.

1. **Единица прогноза это участок хода вокруг входа.** Вход это аварийный
   выход, люк, вентшахта или дверь. Средний участок равен 150 м.
2. **Тревога доступа это одно из двух значений.** «Не замкнут» на контакте
   входа или датчике стекла. «Обнаружено движение» на датчике движения.
   Трубка переговорного устройства, датчики затопления и пожарные датчики в
   событие не входят.
3. **Тревога в окне «Снято с охраны» в событие не входит.** Заказчик снимает
   участок с охраны, чтобы подрядчик законно вошёл в коллектор.
4. **Инцидент это серия тревог на участке с паузами не больше 30 минут.**
5. **Инцидент становится событием при одном из четырёх условий.**
   - Сработал контакт входа или датчик стекла.
   - Сработали два и больше датчиков движения.
   - Датчик движения стоит не дальше 6 пикетов (60 м) от входа.
   - Участок держат меньше двух контактных датчиков.
6. **Метка прогноза равна 1, когда событие наступает в ближайшие 24 часа.**

Из выборки выпадают периоды, где данные врут:

- Первые 270 суток нового объекта. Это пусконаладка.
- Первые 30 суток нового канала.
- Сутки, когда режим охраны не менялся дольше 7 суток и поэтому неизвестен.

Разбор и числа лежат в `backend/docs/adr/0001-access-target.md`.

### Когда прогноз создаёт заявку

Заявка появляется, когда выполнены все три условия.

1. Уровень прогноза `HIGH` или `CRITICAL`.
2. На этом участке по этому направлению нет открытой заявки.
3. Диспетчер недавно не отклонял заявку этого или более высокого уровня.

Срок новой заявки равен половине горизонта от момента расчёта, то есть 12
часам. Срок в конце горизонта привёл бы бригаду к моменту аварии, и заявка
перестала бы быть превентивной. Диспетчер ставит настоящий срок при
подтверждении.

Отклонение глушит новые заявки до названного диспетчером момента. Без ответа
длину выбирает причина: от суток для дубля до месяца для известной особенности
объекта. Рост уровня снимает глушение сразу.

Границы уровней для направления доступа:

| Уровень | Вероятность от | Откуда число |
|---|---|---|
| `MEDIUM` | 0,009 | средняя частота события |
| `HIGH` | 0,156 | порог заявки из цены ошибки |
| `CRITICAL` | 0,2 | первая граница выше `HIGH` |

Остальные направления берут общие границы 0,3, 0,55 и 0,78. Подробности лежат
в `backend/docs/07-auto-orders.md` и `backend/docs/adr/0004-level-thresholds-per-direction.md`.

### Жизненный цикл заявки

Диспетчер работает с прогнозом, а не с заявкой. Решение по прогнозу само
двигает заявку.

1. Прогон создаёт заявку в статусе «Ждёт решения диспетчера» (`AUTO_CREATED`).
2. Диспетчер берёт прогноз в работу и называет итоговый уровень.
   - Уровень `HIGH` или `CRITICAL` переводит заявку в статус «Ждёт бригаду»
     (`CONFIRMED`).
   - Уровень `LOW` или `MEDIUM` отклоняет заявку (`REJECTED`). Выезда нет.
3. Диспетчер назначает бригаду и срок одним действием. Заявка переходит в
   статус «Бригада назначена» (`IN_PROGRESS`).
4. Группа реагирования закрывает заявку с отметкой «факт подтверждён» или
   «факт не подтверждён» и причиной из справочника. Прогноз закрывается вместе
   с заявкой.

Диспетчер может поднять уровень прогноза `LOW` или `MEDIUM` до `HIGH` или
`CRITICAL`. Тогда заявка появляется сразу в статусе «Ждёт бригаду».

| Роль | Видит | Может |
|---|---|---|
| Техник | один комплекс | только читать |
| Диспетчер района | свой район | взять прогноз, принять решение, назначить бригаду, отклонить заявку |
| Диспетчер ОДС | всё предприятие | те же действия на всём предприятии |
| Группа реагирования | всё предприятие | закрыть заявку |

Закрывает заявку только группа реагирования. Отметка о факте потом идёт в
дообучение модели, и ставит её тот, кто был на объекте.

Схема со стрелками лежит в `ARM-ODS-lifecycle.md`.

## Изначально поставленные цели

| Цель | Итог |
|---|---|
| Горизонт прогноза не меньше 24 часов | Выполнено. Прогноз даётся на окно 24 часа |
| Прогноз формируется быстрее 5 минут | Выполнено. Полный прогон на 3 947 единицах занимает 35 с |
| Поток данных обрабатывается быстрее 5 минут | Не выполнено. Потоковая загрузка не сделана, разбор ниже |
| Precision 0,7 и Recall 0,5 | Не достигнуто. Данные не держат такого сигнала, разбор ниже |
| Четыре направления: пожар, доступ, отказ датчика, подтопление | Модель есть у доступа. У отказа датчика готовы метка и витрина. Остальные направления интерфейс показывает на заглушках |
| Веб-интерфейс диспетчера | Выполнено. Дашборд, карта, журнал и заявки |
| Автоматические заявки на обслуживание | Выполнено |
| REST API | Выполнено. Описание OpenAPI лежит по адресу `/api/v1/docs` |
| Роли и вход | Четыре роли, пароль и одноразовый код. Связь с LDAP через Keycloak не поднята |

Прогноз можно давать и заранее, за 24 часа до начала окна. Этот вариант
замерен и включается одной настройкой (`LEAD_DAYS` в `ml/access/panel.py`).
Команда выбрала прогноз на ближайшие сутки: сейчас бригады едут по вызову, а
постоянной охранной бригады нет.

### Почему потоковой загрузки нет

Все данные пришли одной выгрузкой. Настоящий поток заказчик дать не может по
требованиям безопасности и считает заглушку потока ожидаемым решением.
Заглушку мы ещё не написали, поэтому задержку обработки потока не мерили.

Прогноз читает тревоги из Postgres. Данные для обучения модели лежат в
колоночных файлах parquet. Такой файл плохо принимает частые мелкие дописывания,
поэтому свежие факты попадут в него с задержкой. Решение описано в
`backend/TODO.md`, раздел «Загрузка», и не реализовано.

### Почему Precision 0,7 и Recall 0,5 оказались недостижимы

Изначальная цель требует сигнала, которого в источниках данных нет.

1. **Событие редкое.** Проникновение случается на участке в 0,8 % суток.
   Случайный выбор участков даёт точность 0,008.
2. **Больше половины событий приходят без предвестника.** 54 % событий
   случаются после месяца тишины на участке. Журнал датчиков ничего о них не
   говорит заранее.
3. **Правильных ответов в данных нет.** Разметки инцидентов, журнала ОДС и
   истории ремонтов заказчик не передаст. Событие приходится выводить из
   тревог датчиков.
4. **Простое правило тоже слабое.** Правило «событие было вчера» даёт точность
   0,14 на доступе и 0,044 на пожаре. Модель обязана бить именно его.

Что модель даёт на отложенной выборке за первое полугодие 2026 года:

- При той же полноте, что у правила «было вчера», точность модели 0,27 против
  0,14.
- Среди 1 % участков с наибольшим риском событие случается в 20 раз чаще,
  чем в среднем по сети.
- При 5 карточках в сутки модель предупреждает 116 событий из 491. Правило
  «было вчера» предупреждает 67.

Заказчик подтвердил, что 0,7 и 0,5 это значения по умолчанию. Цель хранится на
каждом направлении отдельно, и администратор её правит.

## Запуск

### Только интерфейс на заглушках

Этот вариант не требует сервера. Заглушки держат все четыре направления.

Нужен Node.js 20.19 и выше или 22.12 и выше. Версию показывает `node -v`.

1. Получите код:
   ```
   git clone https://github.com/IIshikiII/LCT2026.git
   cd LCT2026/frontend
   ```
2. Установите зависимости:
   ```
   npm install
   ```
3. Запустите интерфейс:
   ```
   npm run dev
   ```
4. Откройте <http://localhost:5173>.
5. Войдите: логин `ods`, пароль `collector`.
6. При первом входе отсканируйте QR-код приложением-аутентификатором. Введите
   код из него.
   Подходит любое приложение TOTP: Яндекс Ключ, Google Authenticator, Bitwarden
   и другие.

Логины других ролей: `district`, `tech`, `crew`. Пароль у всех `collector`.

### Сервис целиком

Нужны Docker с Compose и Node.js той же версии. Команды шагов 1–7 выполняйте
из папки `backend`.

1. Создайте файл настроек:
   ```
   cp .env.example .env
   ```
2. Поднимите базу и API. Первая сборка образов занимает несколько минут:
   ```
   docker compose up -d db api
   ```
3. Создайте таблицы:
   ```
   docker compose run --rm pipeline uv run --no-sync python -m app.cli migrate
   ```
4. Наполните базу синтетикой и учётными записями:
   ```
   docker compose run --rm pipeline uv run --no-sync python -m app.cli seed
   ```
5. Положите модель рядом с сервисом. На Ubuntu и macOS:
   ```
   mkdir -p artifacts/unauthorized_access
   cp ../ml/access/out/daily_model.joblib artifacts/unauthorized_access/latest.joblib
   cp ../ml/access/out/daily_metrics.json artifacts/unauthorized_access/metrics.json
   ```
   На Windows в PowerShell:
   ```
   New-Item -ItemType Directory -Force artifacts/unauthorized_access
   Copy-Item ../ml/access/out/daily_model.joblib artifacts/unauthorized_access/latest.joblib
   Copy-Item ../ml/access/out/daily_metrics.json artifacts/unauthorized_access/metrics.json
   ```
6. Передайте замер модели на дашборд:
   ```
   docker compose run --rm pipeline uv run --no-sync python -m app.cli publish-metrics
   ```
7. Посчитайте прогнозы. Команда печатает число прогнозов, заявок и время:
   ```
   docker compose run --rm pipeline uv run --no-sync python -m app.cli run-pipeline
   ```
8. Проверьте API: откройте <http://localhost:8000/healthz>.
9. В папке `frontend` создайте файл `.env` с двумя строками:
   ```
   VITE_USE_MOCKS=false
   VITE_API_BASE_URL=http://localhost:8000/api/v1
   ```
10. Запустите интерфейс из папки `frontend`:
    ```
    npm install
    npm run dev
    ```
11. Откройте <http://localhost:5173> и войдите так же, как в первом варианте.

Новые прогнозы появляются только после шага 7. Повторите его, чтобы
пересчитать риск.

### Сервер

Установку на Ubuntu 22.04 делает один скрипт:

```
bash deploy/install.sh
```

Настройки и обновление описаны в `deploy/README.md`.

### Если что-то не работает

| Что видно | Что сделать |
|---|---|
| `Vite requires Node.js version 20.19+` | Обновите Node.js |
| Код входа не подходит | Включите автоматическое время на телефоне. Допуск 30 секунд |
| Порт 5173 занят | Запустите `npm run dev -- --port 5174` |
| Интерфейс не видит API | Проверьте шаг 8 и адрес в `frontend/.env` |
