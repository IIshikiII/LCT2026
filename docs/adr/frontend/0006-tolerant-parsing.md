# ADR 0006. Разбор ответов не бросает исключений

Статус: принято · 2026-09-08

## Контекст

На хакатоне бэкенд меняется каждые два часа. Переименованное поле, съехавший
формат даты, лишний ключ в ответе — норма, а не авария. Строгий разбор в такой
обстановке означает белый экран на защите из-за опечатки в чужом коммите.

## Решение

Все DTO — «мягкие» объекты: `z.looseObject({...})` (в zod 3 — `.passthrough()`).
Разбор идёт через `parseTolerant()`:

```ts
const r = schema.safeParse(raw)
if (r.success) return r.data
console.warn('[api] ответ не прошёл разбор', { url, issues: r.error.issues })
return raw as T
```

То есть zod используется как **описание ожиданий и точка наблюдения**, а не как
охранник на входе.

## Последствия

Хорошее:

- лишнее поле не ошибка, оно доезжает до компонента;
- недостающее поле даёт `undefined` и прочерк в ячейке, а не белый экран;
- расхождение видно в консоли — есть с чем идти к бэкендеру;
- разработка фронта не блокируется готовностью бэкенда.

Плохое, с чем миримся:

- типы `TypeScript` перестают быть гарантией во время выполнения: объявлено
  `probability: number`, а прийти может `undefined`. Поэтому форматтеры в
  `shared/lib/format.ts` обязаны принимать `unknown` и возвращать `'—'` на всём,
  что не разобралось;
- молчаливая деградация может скрыть настоящий баг. Компенсируется тем, что
  `console.warn` громкий и содержит URL и список несоответствий.

## Граница применения

Это решение — про **чтение** ответов. На **запись** (тело действия) валидация
строгая: `buildZodSchema()` по `action.fields` не пускает форму с незаполненным
обязательным полем. Отправить мусор на сервер нельзя, принять мусор от сервера —
можно.

## Когда пересмотреть

После хакатона, когда контракт стабилизируется: тогда `parseTolerant` стоит
перевести в режим «бросать в dev, деградировать в prod».
