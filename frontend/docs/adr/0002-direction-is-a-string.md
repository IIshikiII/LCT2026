# ADR 0002. Направление, уровень и статус — строки, а не union

Статус: принято · 2026-09-08

## Контекст

ТЗ перечисляет четыре направления прогнозирования и разрешает делать одно или
несколько. Набор почти наверняка поменяется: на защите может появиться пятое, у
заказчика — своё. То же с уровнями риска и статусами заявки.

Естественный для TypeScript ход — union-типы:

```ts
type Direction = 'FIRE_RISK' | 'SENSOR_FAILURE' | 'UNAUTHORIZED_ACCESS' | 'WEAR_OUT'
```

## Решение

`direction`, `level`, `status` типизируются как `string`. Всё, что фронт знает о
предметной области, приходит в `GET /meta` и лежит в реестрах.

Ни одного `switch` по коду направления. Ни одной карты `Record<DirectionCode, ...>`,
захардкоженной в коде приложения.

## Последствия

Хорошее:

- пятое направление появляется в фильтрах, на карте и на дашборде без правок кода
  фронтенда — это проверяется тестом `src/mocks/flexibility.test.tsx`;
- рассинхрон фронта и бэкенда не ломает сборку и не роняет экран: неизвестный код
  получает синтезированную мету (подпись = код, цвет = хеш кода).

Плохое, с чем миримся:

- компилятор больше не подсказывает опечатку в коде направления;
- «где обрабатывается FIRE_RISK» невозможно найти поиском по коду приложения —
  ответ всегда «в `src/mocks/directions/fireRisk.ts` или на бэкенде».

Второй пункт — цена за то, что доменная логика вынесена из UI, а не размазана по
нему. Компенсируется тем, что все направления собраны в одном каталоге плагинов.

## Проверка

`src/architecture.test.ts` падает при появлении union-типа по этим полям и при
`switch` по `direction`.
