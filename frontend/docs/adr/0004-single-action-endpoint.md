# ADR 0004. Один эндпоинт действий вместо ручки на кнопку

Статус: принято · 2026-09-08

## Контекст

Диспетчер делает с прогнозом несколько вещей: подтверждает заявку, отклоняет
прогноз с указанием причины, назначает осмотр, закрывает заявку с разметкой.
Набор действий зависит от направления, статуса и, скорее всего, от роли — и он
будет меняться в течение хакатона.

## Решение

```
POST /predictions/{id}/actions/{code}   тело = плоский объект значений полей
POST /orders/{id}/actions/{code}
```

Список доступных действий приходит вместе с сущностью:

```ts
interface ActionDef {
  code: string
  label: string
  kind: 'primary' | 'secondary' | 'danger'
  confirm?: string
  fields: FieldDef[]
}
```

Форма строится по `fields` (`DynamicForm` + `buildZodSchema`). Ответ — обновлённая
сущность целиком, она кладётся в кэш Query.

## Последствия

Хорошее:

- новое действие добавляется **только на бэкенде**: фронт нарисует кнопку и форму
  сам;
- фронт не угадывает, что изменилось после действия, — сервер присылает состояние
  целиком;
- невозможна ситуация «кнопка есть, а нельзя»: список действий приходит уже
  отфильтрованным под текущий статус.

Плохое, с чем миримся:

- контракт менее самоописателен: по OpenAPI не видно, какие бывают `code`.
  Компенсируется тем, что коды перечислены в
  [02-api-contract.md](../02-api-contract.md) и в моках;
- нестандартный UI действия всё же требует кода на фронте. Для этого есть
  `actionRegistry`, но им пользуется ровно одно действие — закрытие заявки.

## Исключение

`close` для заявки имеет собственную форму (`CloseOrderForm`): отметка «прогноз
подтвердился / не подтвердился» обязательна и должна быть радиовыбором, а не
чекбоксом, — из неё считаются Precision и Recall на реальных данных, и «не
тронул чекбокс» не должно молча означать «не подтвердился».
