# ADR 0003. Тело карточки — массив блоков из API, а не вёрстка

Статус: принято · 2026-09-08

## Контекст

Карточка прогноза должна объяснять, почему модель считает объект рискованным.
Объяснение у направлений разное: у отказа датчика — доля ложных сработок и
история ремонтов, у пожарного риска — динамика температуры и близкие сварочные
работы, у подтопления — уровень воды и частота включения насосов.

Прямолинейный путь — четыре компонента карточки и выбор по направлению. Он же —
прямая дорога к `switch (direction)` и к тому, что новое направление означает
новый компонент.

## Решение

Бэкенд отдаёт `blocks: [{ type, title, data }]`. `data` — намеренно `unknown`:
его форму знает только компонент блока.

Фронт держит реестр `type → компонент` и запасной `GenericBlock`, который
рекурсивно рисует любой JSON парами «ключ — значение» и таблицами для массивов
объектов. Каждый блок обёрнут в `ErrorBoundary`.

## Последствия

Хорошее:

- новое направление приносит свои блоки и отображается сразу, пусть и
  «некрасиво» — информация видна с первой минуты;
- новый тип блока — один файл и одна строка в реестре;
- сломанные данные в одном блоке не уносят карточку.

Плохое, с чем миримся:

- вёрстку карточки нельзя спроектировать целиком: композиция определяется
  бэкендом. Компенсируется тем, что порядок блоков задаёт бэкенд же, и он его
  контролирует осмысленно;
- типизация `data` — на совести компонента блока. Поэтому каждый блок обязан
  разбирать `block.data` своей zod-схемой и при неудаче деградировать до
  `GenericBlock`, а не бросать.

## Проверка

`src/card/blockRegistry.test.tsx`: неизвестный тип → `GenericBlock`; блок,
бросающий исключение, → `BlockError`, соседние блоки живы.
