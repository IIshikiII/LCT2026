# ADR 0011. SHAP показывает блок `factors`, а не новый тип блока

Статус: принято · 2026-09-20

## Контекст

Направление `UNAUTHORIZED_ACCESS` объясняет каждый прогноз через SHAP.
Метод `explain()` плагина `backend/app/ml/plugins/unauthorized_access.py`
считает вклад 17 признаков в логарифме шансов и приводит его к диапазону от
минус 1 до 1 правилом `вес = tanh(вклад / 2)`.

Карточка диспетчера уже умеет показывать такие числа. Блок `factors` и
компонент `FactorsBlock` рисуют полосы в обе стороны от нуля. Вправо признак
повышает риск, влево снижает. Форма данных совпадает с тем, что отдаёт плагин,
поле в поле.

Три остальных направления тоже дают блок `factors`, но их веса приходят из
эвристик заглушек, а не из модели.

Надо выбрать одно из двух. Первое: расширить блок `factors`. Второе: завести
новый тип блока, например `shap`, и новый компонент в реестре.

## Решение

Тип блока остаётся `factors`. Новый тип не заводится, реестр
`src/card/blockRegistry.tsx` не меняется.

Форма данных блока получает одно новое поле:

```json
{
  "items": [
    { "label": "Тревог вне режима охраны за 24 часа", "weight": 0.71, "value": "4" },
    { "label": "Часов с последней тревоги", "weight": -0.22, "value": "31" }
  ],
  "note": "Полосы показывают силу и направление фактора, а не слагаемые вероятности."
}
```

Поле `note` необязательное. Строки `items` бэкенд отдаёт отсортированными по
модулю веса, сильнейшая первой.

Меняются три правила показа.

1. **Ось фиксирована на плюс-минус 1.** Сейчас компонент делит вес на
   наибольший вес списка. Это надо убрать.
2. **Длинный список сворачивается.** Видны первые шесть строк, остальные
   открывает кнопка «Ещё N факторов».
3. **Вес вне диапазона прижимается к границе.** Полоса рисуется полной,
   строка не пропадает и блок не падает.

Бэкенд отбрасывает слабые факторы: строка остаётся, если её вес по модулю не
меньше 0,02. Такой вес меняет шанс события на 4 %. Первые три строки остаются
всегда, даже когда все веса малы.

Ниже полос стоит строка `note`. Она отвечает на вопрос, который диспетчер
задаёт первым: почему полосы не складываются в вероятность из шапки карточки.
Полный разбор лежит в докстроке `shap_weight`.

## Обоснование

### Почему не новый тип блока

Тип блока называет форму данных, а не её происхождение. SHAP это способ
получить веса. Направление сменит модель на логистическую регрессию или на
перестановочную важность, веса останутся теми же числами от минус 1 до 1, а имя
типа `shap` станет неправдой.

Один вопрос требует одного вида. Диспетчер открывает карточки четырёх
направлений подряд и задаёт им один вопрос: что двигало прогноз и в какую
сторону. Два разных вида ответа на один вопрос он читает дважды медленнее.

Новый компонент повторил бы старый. Полосы, знак, подпись значения и порядок
строк нужны обоим. Разошлись бы они на первой правке, и одно направление
осталось бы со старым видом.

Запрета на новый тип нет: реестр `type → компонент` для того и сделан
(ADR 0003), и правило 2 из `CLAUDE.md` он не нарушает. Отказ от нового типа
это выбор по цене, а не по запрету.

### Почему фон не показан

SHAP даёт ещё одно число: фоновое значение, средний риск направления. Полосой
его показывать нельзя. Фон это точка отсчёта, а не фактор, и рядом с факторами
он зовёт их сложить. Вероятность прогноза уже стоит в шапке карточки. Место
фона занимает строка `note`.

### Почему ось фиксирована

Бэкенд считает вес по правилу, которое не зависит ни от набора признаков
строки, ни от переобучения модели. Масштаб один во всех карточках, и это
свойство держит сравнение карточек глазом.

Нормировка по максимуму списка это свойство ломает. Карточка без сильных
факторов покажет полную полосу у веса 0,05, и рядом с карточкой, где главный
фактор весит 0,9, обе выглядят одинаково.

Замер T14 на отложенной выборке 2026 года: у прогнозов выше порога вес главного
фактора лежит между 0,51 и 0,96 при медиане 0,69. Фиксированная ось занята
делом. Заглушки дают веса от 0,1 до 0,9, поэтому им фиксированная ось тоже
годится.

### Почему список режет фронт, а не бэкенд

Сколько строк влезает в правую панель, знает вёрстка. Бэкенд знает только силу
фактора. Поэтому бэкенд отбрасывает факторы по смыслу, то есть те, что ничего
не меняют, а фронт прячет остаток по месту.

## Последствия

Хорошее:

- задача T22 это правка одного компонента, а не новый компонент и новая строка
  реестра;
- поле `note` старый фронт молча пропускает: схема блока разбирается через
  `z.looseObject` (ADR 0006). Бэкенд выкатывается раньше фронта без поломки;
- фиксированную ось и сворачивание получают все четыре направления сразу.

Плата:

- карточка со слабыми факторами станет визуально пустой. Это честно, но
  требует, чтобы строка показывала `value`. Без него короткая полоса не несёт
  ничего;
- порог отсева 0,02 живёт числом в коде бэкенда. Он скрывает часть картины,
  поэтому стоит рядом с `shap_weight` и меняется вместе с правилом веса.

строк, блок без поля `note`.
