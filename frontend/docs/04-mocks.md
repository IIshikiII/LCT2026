# Заглушки

Вся имитация бэкенда живёт в **`src/mocks/`** и больше нигде. Приложение целиком
работает без сервера: `VITE_USE_MOCKS=true`.

## Зачем это отдельная папка

`src/mocks/` — это не «моки для тестов». Это **стенд-ин бэкенда**: он знает
предметную область, которую приложение знать не должно. Здесь и только здесь
написаны слова «пожарный риск», «отказ датчика», «несанкционированный доступ»,
«задымление». Остальной код видит их как строки из `/meta`.

Отсюда правило: **ничто вне `src/mocks/` не импортирует из `src/mocks/`**, кроме
одной строки в `src/main.tsx` и тестового сервера в `src/test/`. Удали папку —
приложение соберётся и пойдёт на реальный API.
См. [adr/0007-mocks-as-a-backend-stub.md](../../docs/adr/frontend/0007-mocks-as-a-backend-stub.md).

## Направления как плагины

Все базовые направления реализованы одинаково — модулем, который отвечает
интерфейсу `DirectionPlugin`:

```ts
interface DirectionPlugin {
  meta: DirectionMeta                      // code, label, shortLabel, accent, minHorizonHours
  reasons: ReasonOption[]                  // справочник фактических причин
  workTypes: string[]                      // виды работ для автозаявки
  quality: { precision: number; recall: number }   // для виджета метрик ТЗ
  appliesTo(facility: Facility): boolean   // каким объектам направление вообще подходит
  summary(ctx): string                     // одна строка человеческим языком
  blocks(ctx): CardBlock[]                 // тело карточки прогноза
  actions(ctx): ActionDef[]                // кнопки карточки
}
```

Это единственное место во всём фронтенде, где направления различаются. Генератор
данных перебирает плагины и не знает, сколько их.

Что в каком направлении лежит:

| Код | Подпись | Объекты | Ключевые блоки карточки |
|---|---|---|---|
| `SENSOR_FAILURE` | Отказ датчика | датчики СМВУ | `factors` (доля ложных сработок, «шум», возраст, история ремонтов), `timeseries` (сработки по дням), `timeline` (ремонты и поверки) |
| `FIRE_RISK` | Пожарный риск | камеры и участки с кабелем | `factors` (температура, дым, сварочные работы рядом), `timeseries` (температура и задымление), `table` (допуски АРМ-Контроль на горячие работы) |
| `UNAUTHORIZED_ACCESS` | Несанкц. доступ | люки, входные камеры | `factors` (ночные срабатывания, доступ без допуска, серия), `timeline` (журнал доступов), `table` (действующие допуски) |
| `FLOOD_RISK` | Риск подтопления | *выключено* | добавляется дев-панелью, служит доказательством гибкости |

Плюс у каждого прогноза есть блок с **намеренно неизвестным типом**
(`type: 'unknown-experimental'`) у небольшой доли записей — чтобы на демо было
видно, что `GenericBlock` работает.

## Детерминированность

`faker.seed(SEED)` в `db/rng.ts`, `SEED = 20260908`. Данные одинаковы между
перезапусками: демо на защите воспроизводимо, скриншоты не «плывут», тесты
стабильны.

Все относительные даты считаются от `db().now` — одного зафиксированного момента,
а не от `Date.now()`. Иначе тест «горизонт ≥ 24 ч» стал бы мигающим.

## Объём сида

- 8 коллекторов, ~90 участков, 5 районов, ~600 объектов;
- координаты — синтетические полилинии в пределах МКАД;
- ~260 прогнозов, распределены по четырём направлениям и четырём уровням риска,
  **у всех `horizonHours >= 24`** (метрика ТЗ);
- `computeMs` — правдоподобно ниже 5 минут, с разбросом (метрика ТЗ);
- ~90 заявок во всех статусах, часть связана с прогнозами через `predictionId`;
- метрики моделей: у двух направлений выше целевых, у одного на грани — чтобы
  виджет метрик было видно и в зелёном, и в красном состоянии.

Правдоподобие: в рядах телеметрии есть суточная и сезонная составляющие, часть
датчиков «шумные» — с растущей долей ложных сработок в истории.

Задержка ответов 150–500 мс — чтобы скелеты и спиннеры были видны и отлажены.

## Дев-панель

Кнопка в правом нижнем углу, только при `VITE_USE_MOCKS=true`. Переключатели
хранятся в `localStorage` и читаются хендлерами:

| Флаг | Что делает | Зачем |
|---|---|---|
| Сломать `/meta` | `/meta` отвечает 500 | Показать, что приложение поднимается на `FALLBACK_META` |
| Новое направление | В `/meta` и в данные добавляется `FLOOD_RISK` | Тест на гибкость вживую, без пересборки |
| Медленная сеть | Задержка 2–4 с | Проверить скелеты |
| Ошибки списков | `/predictions` отвечает 500 | Проверить `ErrorState` |

## Типовые правки

### Добавить направление

1. `src/mocks/directions/myDirection.ts` — реализовать `DirectionPlugin`.
2. Добавить в массив в `src/mocks/directions/index.ts`.

Всё. Направление появится в `/meta`, в прогнозах, в фильтрах, на карте, на
дашборде и в виджете метрик. **Код вне `src/mocks/` не трогается** — это и есть
проверка главного архитектурного принципа.

### Добавить тип блока в карточку

Возвращать его из `blocks()` нужного плагина. Пока в
`src/card/blockRegistry.tsx` нет компонента — блок нарисуется `GenericBlock`.

### Добавить ручку

См. [02-api-contract.md](02-api-contract.md#как-добавить-ручку-пример-целиком).
Хендлер в `handlers.ts` + данные в `db/`.

## Вход и роли

Заглушка отказывает без токена так же, как сервер: 401 на любую ручку, кроме
двух шагов входа. Иначе экран входа можно было бы обойти, и `VITE_USE_MOCKS=true`
перестал бы быть правдой.

Учётных записей четыре, по одной на роль из ответа заказчика 4.1: `ods`,
`district`, `tech`, `crew`. Пароль у всех `collector`. У записи `crew` ключ
второго фактора не заведён — так первый вход показывает регистрацию ключа
целиком.

Роль работает по-настоящему: границы видимости режут прогнозы, заявки, карту и
дашборд, а список действий приходит отобранным по правам. Смена роли меняет
экран без единой правки кода.

Одноразовый код заглушка считает **по-настоящему**, по RFC 6238. Секрет она
выдаёт сама при регистрации ключа, значит и проверить код может. Режима
«подойдут любые шесть цифр» нет: он превращал бы второй фактор в декорацию.
Считает Web Crypto, реализация лежит в `db/totp.ts` и зеркалит
`backend/app/auth/totp.py`.

Отсюда следствие для тестов: код надо посчитать, а не выдумать. Помощник
`mockCodeFor(username)` из `handlers.ts` делает это по тому же секрету, что
ушёл в QR.

Панель тестового стенда в заглушках включена всегда, и наборы учёток работают
целиком: создание, удаление, отметка о втором факторе. Настоящий сервер смотрит
на флаг `TEST_STAND`.

## Заглушки в тестах

`src/test/msw.ts` поднимает `setupServer` с теми же `handlers.ts`. То есть тесты
ходят в те же данные, что и живое приложение, — расхождению между «работает в
браузере» и «зелёные тесты» неоткуда взяться.

Каждый тест начинается с открытой смены диспетчера ОДС: `src/test/setup.ts`
зовёт `signInAs('ods')`. Тест роли переключается одной строкой —
`signInAs('tech')`, — и тот же экран показывает границу видимости техника.
