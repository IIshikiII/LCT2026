# Тесты

Vitest + Testing Library + jsdom. Тесты лежат рядом с кодом (`*.test.ts[x]`),
а не в отдельном дереве: так их видно при правке и труднее забыть.

```
npm test           один прогон
npm run test:watch наблюдение
npm run test:ui    браузерный интерфейс Vitest
```

## Что мы проверяем и что не проверяем

Тесты здесь — не про покрытие процентами. Они закрывают ровно две вещи:

1. **Критерии приёмки из спецификации (§12).** Каждый пункт — тест. Если пункт
   нельзя проверить тестом, он сформулирован плохо.
2. **Инварианты устойчивости.** «Неизвестное не роняет экран» — утверждение,
   которое ломается при первой же неаккуратной правке, если его не держать тестом.

Мы **не** тестируем: вёрстку попиксельно, MapLibre (требует WebGL, в jsdom не
живёт), Recharts (рисует SVG по размеру контейнера, в jsdom нулевому).

## Архитектурный тест

`src/architecture.test.ts` читает исходники и падает, если находит:

- union-тип по кодам направлений/уровней/статусов;
- `switch` по полю `direction`;
- доменные слова («пожарн», «датчик», «несанкционир», «задымлен») вне `src/mocks/`;
- импорт из `src/mocks/` вне разрешённого списка файлов.

Это дешёвый способ не дать архитектурному принципу размыться за неделю
интенсивной разработки. Если тест мешает — значит, либо правка неверна, либо
принцип пора обсуждать явно и менять ADR, а не обходить проверку.

## Хелперы

`src/test/renderWithProviders.tsx`

```ts
renderWithProviders(<AppShell />, { route: '/journal?level=HIGH' })
```

Оборачивает в `QueryClientProvider` (с выключенными ретраями и `gcTime: 0`) и в
`MemoryRouter` с заданным маршрутом. Обёртки `Routes` нет: ни один экран не
читает параметры пути, всё состояние живёт в параметрах запроса.

`currentSearch()` и `currentPath()` возвращают текущий адрес — так проверяется,
что действие записало в URL то, что нужно.

`src/test/msw.ts` — `setupServer` на тех же `handlers.ts`, что и браузер.
Поднимается в `src/test/setup.ts` глобально: `beforeAll(listen)`,
`afterEach(resetHandlers)`, `afterAll(close)`.

Подменить ответ в одном тесте:

```ts
server.use(http.get('*/meta', () => new HttpResponse(null, { status: 500 })))
```

## Как писать новый тест

Порядок в этом проекте — **документация, затем тест, затем код**. На практике:

1. Опиши поведение в нужном документе `docs/` одной строкой таблицы.
2. Напиши падающий тест, который это поведение формулирует.
3. Напиши код до зелёного.

Правило именования: `describe` — имя модуля, `it` — предложение на русском,
описывающее поведение, а не реализацию. `it('рисует запасной блок для неизвестного
типа')`, а не `it('returns GenericBlock')`.

## Асинхронность

В браузере данные приходят с задержкой 150–500 мс: моки имитируют сеть, чтобы
скелеты и спиннеры были видны и отлажены. В тестах `src/mocks/handlers.ts`
отключает задержку, проверяя `import.meta.env.MODE === 'test'`.

Задержка всё равно не нулевая — запрос проходит через MSW. Поэтому `findBy*` и
`await waitFor`, никогда `getBy*` сразу после рендера.

Общий `testTimeout` поднят до 20 секунд (`vite.config.ts`): интеграционные тесты
поднимают весь каркас и ждут повторных попыток запросов.
