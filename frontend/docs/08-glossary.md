# Глоссарий

Термины предметной области — чтобы не гадать при чтении кода и мок-данных.

## Организация и системы

**АО «Москоллектор»** — эксплуатирует 825 км подземных коллекторов Москвы: в них
проложено ~19,7 тыс. км кабелей связи, 8,3 тыс. км силовых кабелей, 1,9 тыс. км
тепловых и водопроводных сетей.

**ОДС** — объединённая диспетчерская служба. Диспетчер ОДС — пользователь этого
интерфейса. Он видит срабатывания, решает, выезжать ли, и закрывает заявки.

**СМВУ** — система мониторинга и внутреннего управления: сеть датчиков в
коллекторах (контактные, объёмные, температурные, дымовые, газовые) и журнал их
срабатываний. Исторические логи за 12+ лет — основной обучающий материал модели.

**АРМ-Контроль** — система допусков: кто, когда и с каким видом работ заходит в
коллектор. Даёт корреляцию «сварочные работы → рост пожарного риска» и признак
«доступ без допуска» для несанкционированного доступа.

**ОЭ** — отдел эксплуатации. Реестр фондов по районам (вентшахты, насосы, камеры,
датчики, люки) с датами ввода и историей ремонтов, плюс визуальные обследования.

**ППР / ТО** — планово-предупредительный ремонт / техническое обслуживание.
Сегодня выполняются по регламентным срокам; смысл проекта — перейти к
обслуживанию по фактическому состоянию.

## Инфраструктура

**Коллектор** — подземное сооружение, в котором проложены сети. В сиде их 8.

**Участок (пикет)** — отрезок коллектора между камерами. Единица планирования
работ. В сиде ~90.

**Камера** — помещение коллектора, где сходятся участки; место установки
оборудования и датчиков.

**Вентшахта** — вентиляционная шахта коллектора.

**Люк** — точка входа. Основной объект для направления «несанкционированный
доступ».

**Объект (facility)** — то, на что делается прогноз: датчик, камера, вентшахта,
насос, люк, участок. В коде — `FacilityRef` с иерархией
`коллектор → участок → камера → устройство`.

## Прогнозирование

**Направление прогнозирования** — класс предсказываемых событий. В ТЗ их четыре:
отказ датчика, пожарный риск, несанкционированный доступ, износ инфраструктуры.
**В коде фронтенда направление — просто строка из `/meta`**, см.
[03-extension-points.md](03-extension-points.md).

**Горизонт (`horizonHours`)** — на сколько часов вперёд смотрит прогноз. По ТЗ
не менее 24. Проверяется и в сиде, и в виджете метрик.

**Уровень риска (`level`)** — `LOW` / `MEDIUM` / `HIGH` / `CRITICAL`. Тоже строка
из `/meta`, у каждого уровня есть `order` и `colorVar`.

**Ложная сработка** — датчик сработал, проверка ничего не нашла. Значительная
часть срабатываний СМВУ такие; доля и динамика ложных сработок — основной признак
деградации датчика.

**Precision / Recall** — метрики качества модели. По ТЗ: Precision > 0.7,
Recall > 0.5 на тестовой выборке. Считаются на реальных данных из отметки
«прогноз подтвердился» при закрытии заявки.

**Время формирования прогноза (`computeMs`)** — по ТЗ < 5 минут. Показывается
в виджете «состояние конвейера».

## Работа диспетчера

**Прогноз (`Prediction`)** — запись «на объекте X с вероятностью p в ближайшие N
часов произойдёт событие направления D». Статусы: `NEW`, `IN_REVIEW`,
`ORDER_CONFIRMED`, `REJECTED`, `CLOSED`.

**Заявка (`WorkOrder`)** — задание на превентивное обслуживание. Создаётся
системой автоматически из прогноза (`AUTO_CREATED`), диспетчер подтверждает
(`CONFIRMED`) или отклоняет (`REJECTED`), бригада выполняет (`IN_PROGRESS`),
диспетчер закрывает (`DONE`). Терминальный статус заявки — `DONE`, прогноза —
`CLOSED`. Коды разные намеренно: это разные сущности с разным жизненным циклом.

**Разметка при закрытии (`outcome`)** — фактическая причина + обязательная отметка
«прогноз подтвердился / не подтвердился» + комментарий. Это единственный источник
честного качества модели на реальных данных, поэтому поле обязательное.

**Свежесть данных (`freshnessMinutes`)** — сколько минут прошло с последнего
успешного расчёта. Показывается в шапке: диспетчер должен понимать, смотрит он на
актуальную картину или на вчерашнюю.
